Состояние реализации и доказательства проверок — в `docs/implementation/progress.md`; сведения об отдельной публикации интерфейса — в `docs/implementation/sites-hosting.md`.

Их первоначальные задачи завершены, включая браузерные сценарии V1–V6 и проверки восстановления. Согласованные документы и `docs/architecture/implementation-contracts.md` остаются базой существующего поведения. Конкретные технические предложения планов приняты в описанном объёме; оставленные открытыми вопросы не получают произвольных ответов. Не начинать завершённую реализацию заново с V0 и не запрашивать повторное одобрение тех же планов.

Прежнее условие «не создавать plan.md/tasks.md до анализа и согласования спецификаций» выполнено для первоначального MVP. Новые изменения определяются текущим поручением пользователя; не считать старые выполненные задачи очередью новой работы. Учитывать только явно подтверждённые изменения объёма; отсутствие ответа не считать согласием. Реализованный MVP не означает готовность публичного production-развёртывания: полноценная регистрация и production-вход пользователей пока не реализованы, нагрузочный SLO не подтверждён локальным smoke.

## Новые функции и изменения

- Пользователь описывает желаемое поведение; агент самостоятельно определяет затронутые сервисы, сценарии, API, сообщения, схему БД, frontend, документацию и тесты. Не требовать от пользователя перечня связанных файлов.
- Для новой бизнес-функции или изменения бизнес-правил сначала разобрать требования, критерии приёмки, влияние и неизвестные значения; подготовить соразмерные изменения спецификации, плана и задач. До реализации согласовать неразрешённые бизнес-вопросы и существенные изменения объёма. Уже явно согласованные решения не отправлять на повторное согласование.
- Небольшие исправления ошибок и оформления без изменения бизнес-правил выполнять в рамках поручения сразу; не создавать отдельную спецификацию/план/задачи ради формальности.
- Обновлять только действительно затронутые документы и потребителей контрактов вместе с реализацией. Сохранять историю одобрений и отдельно фиксировать новые решения, выполненные проверки и оставшиеся ограничения.
- Исходные исключения из MVP описывают утверждённый объём первой реализации. Новое явное поручение пользователя может расширить этот объём; такое изменение нужно отразить в затронутых документах, не расширяя соседние процессы по собственной инициативе.

## Границы MVP

- Проверка решений жюри, отказ и передача старшему жюри.
- Результаты команд и онлайн-таблица.
- Апелляции, перепроверка и согласованное обновление результатов.
- Реализуемый объём — только Checking, Results и Appeals. Загрузка/приём решений, фотографирование, определение задачи по QR или вручную, генерация бланков, управление турниром и вопросы исключены последним уточнением пользователя (D24).
- Для сквозных тестов подготавливаются уже принятые/идентифицированные решения, их неизменяемые ссылки на материал и проверки. Это тестовые данные, не API или модуль загрузки. Локальный тестовый вход допускается; настоящая регистрация должна быть возможна позже.

## Реализованные технологии и границы

Backend: C#, ASP.NET Core, .NET 10. Frontend: React, TypeScript, Vite. У каждого микросервиса собственная PostgreSQL БД. Локальная среда — Docker Compose. Межсервисная связь — API и асинхронные сообщения.

Реализованы сервисы Checking, Results, Appeals. Checking владеет проверками и локальными ссылками на уже принятое решение, а не модулем приёма/загрузки или агрегатом подачи. Не создавать дополнительные сервисы по одному на агрегат или экран.

## Правила проектирования

Согласовано пользователем 23 октября 2026 года: команда не отправляет решение одной задачи повторно; каждый член жюри может проверять любую задачу и имеет не более одной незавершённой проверки; после отказа обычного проверяющего решение поступает старшему жюри для окончательного вердикта и ожидает в его очереди, если старший занят. Вердикт старшего после такой передачи нельзя обжаловать.

Дополнительно согласовано: после успешной передачи отказной работы в очередь старшего обычный проверяющий свободен и может брать следующую; закрытие страницы или потеря связи сохраняет назначение за прежним проверяющим и при возвращении он продолжает ту же проверку. Не вводить автоматическое освобождение по отсутствию связи/таймауту. Ручное освобождение длительно зависшего назначения и полномочия для него остаются предложением, не подтверждённым отдельно.

Результаты публикуются автоматически после обработки вердикта Results, включая коррекции по апелляции. Итог команды — сумма баллов по задачам; при равенстве суммы команды делят место без дополнительных критериев. Места нумеруются без пропусков: 1, 1, 2. Общая таблица с баллами каждой команды по задачам доступна всем командам и посетителям без входа. Это не открывает доступ к материалам решений, действиям жюри и подаче апелляций.

Апелляция подаётся после публикации результата в любое время до конца турнира, без интервала от публикации. Турнир завершает организатор своим действием, не расписание. Поданные вовремя апелляции можно брать и завершать после конца турнира. Член жюри вручную выбирает апелляцию и сам перепроверяет с общим лимитом одной проверки; это может быть первоначальный проверяющий. Одна подача не запускает автоматическую перепроверку. Разрешена одна апелляция команды на задачу турнира за весь процесс, не на версию/активный статус; закрытие/коррекция не разрешают новую. Вердикт старшего после обычной передачи не обжалуется. Полное управление турниром по-прежнему вне MVP: для тестирования нужен только отдельный адаптер факта ручного завершения и согласованная граница закрытия подачи, без новых турнирных CRUD-процессов.

Если выбравший апелляцию жюри отказался, та же перепроверка передаётся в очередь старшего для окончательного вердикта; отказавшийся свободен. Это согласованное исключение из личного исполнения выбравшим: не создавать новую апелляцию или второй Check. Первичные решения, принятые до конца турнира, также можно брать и завершать после него. Комментарии жюри к любому вердикту, включая неправильное решение и итог апелляции, в MVP не нужны; сохраняются структурированный исход, авторство и история, а не поле комментария.

Дополнительно согласованы: стоимость задачи задана до турнира и неизменна; локальное переключение тестовых пользователей подходит, позже нужна полноценная регистрация. Изолировать dev-выдачу удостоверения, сохранять внутренние ID/серверные права при замене поставщика. Фото листа с QR описывает будущий внешний приём; по окончательному уточнению D24 он целиком вне текущего объёма.

- Разделять подтверждённые правила диаграммы, технические предложения и неизвестные требования. Ссылаться на идентификаторы `C`, `E`, `P`, `A`, `RM` исходной диаграммы и вопросы `Qxx` архитектуры.
- Бизнес-правило и запись принадлежат одному сервису. Запрещены прямой доступ к чужой БД, межсервисные FK, общие ORM-сущности и общие бизнес-агрегаты.
- Проверка выносит вердикт; Results рассчитывает и публикует баллы; Appeals управляет жизненным циклом апелляции. Не дублировать эти полномочия.
- Не полагаться на доставку exactly-once или глобальный порядок сообщений. Проектировать outbox, inbox, идемпотентность, контроль версий, восстановление и аудит вместе с процессом.
- Нельзя считать повтор HTTP-запроса новой бизнес-операцией. Нельзя перезаписывать новый результат устаревшей перепроверкой.
- Различать отсутствие результата, отрицательный вердикт и незавершённую синхронизацию. Frontend не является владельцем итоговых баллов или прав доступа.
- Не подставлять сроки, лимиты, правила ранжирования, частичные баллы и правила повторной отправки по собственному усмотрению.
- Контракты API и сообщений проектировать отдельно от внутренних моделей. Изменение контракта проверять у всех известных потребителей.

## Работа с документацией и дальнейшая проверка

Обновлять связанные документы вместе; сохранять статус одобренных спецификаций и дату одобрения, отличая их от архитектурных черновиков, и вести список нерешённых вопросов. Не возвращать согласованные правила в неопределённое состояние без нового указания пользователя. Предлагаемая структура каталогов не означает поручение создать её целиком.

При изменении реализации проверять прежде всего затронутые бизнес-инварианты: конкурентное назначение, повтор команды, дубли и перестановку событий, восстановление после сбоя и устаревшую апелляцию. Не обещать работоспособность по одному наличию файлов или успешной сборке. Тесты приложения существуют: backend, frontend, контракты, fixtures, PostgreSQL/broker integration и браузерные E2E. Последний полный прогон от 24 октября 2026 — 441 тест; отдельные integration/E2E-доказательства приведены в журнале. Это исторический результат, а не автоматическое подтверждение будущих изменений.

Общий набор — `./scripts/check.ps1` (с `-Restore`, когда требуется восстановление зависимостей). Проверка документов — `node scripts/check-docs.mjs`; границ проектов — `node scripts/check-architecture.mjs`. PostgreSQL/broker gates — `node scripts/check-checking-storage.mjs`, `node scripts/check-results-storage.mjs`, `node scripts/check-appeals-storage.mjs`. Выбирать проверки по изменению; для чисто документационных правок достаточно целостности документов/ссылок и Git diff. Не перезапускать весь набор без причины после успешных подходящих проверок.

## Локальная среда, данные и публикация

Локальный интерфейс запускается через `npm run dev:web`, адрес `http://127.0.0.1:5173`; Vite проксирует три API на порты 5101/5102/5103. Проверять фактическую готовность API/БД/брокера и реальные запросы через frontend, не только факт запуска процесса. Local/Test поддерживают переключение тестовых субъектов; production-сборка не содержит этого переключателя.

Существующие Docker volumes, секреты, ключи и бизнес-состояние сохранять. Перед запуском выяснять, какой Compose-проект и данные нужны пользователю. Последний проверенный локальный проект — `matigr-e2e-final`; его тестовый турнир завершён вручную, новые апелляции закрыты, первичные проверки и апелляции завершены. Не открывать окно заново, не освобождать назначения и не сбрасывать квоты ради демонстрации. Сквозные/fault scripts могут менять данные и останавливать сервисы: предварительно читать сценарий и выполнять на явно выбранном изолированном тестовом проекте, а не на пользовательском стеке. Без отдельного поручения не удалять volumes, не делать factory reset и не заменять существующие ключи.

Её идентификаторы, URL, источник и ограничения — в `docs/implementation/sites-hosting.md`; использовать существующий Site при поручении обновления. Отдельный Sites checkout исключён из основного репозитория через `/sites/`; не публиковать с ним локальные данные/секреты и не подменять реальные API имитацией ответов. Публичное развёртывание backend, production-аутентификация и изменение аудитории требуют соответствующей новой задачи.
