# Results: хранение, применение и чтение

RES-BE-01–04 реализуют собственную модель и PostgreSQL Results. Проверка/назначения принадлежат Checking; допустимость подачи и квота — Appeals. Межсервисных FK, общих ORM/доменных сущностей и API начисления из браузера нет.

`team_task_results` уникален по tournament/team/task, закрепляет solution/material и текущую публикацию. `result_publications` хранит неизменяемые снимки и UNIQUE(result/version). `evaluation_receipts` имеет PK checkId и semantic hash; terminal Applied/Rejected отделены от Deferred. Баллы numeric(28,0), версии bigint; wire-значения — десятичные строки. `tournament_snapshots` задаёт порядок commit турнира. Roster/rules, inbox/outbox и диагностика находятся только в этой БД.

Local startup применяет миграцию и импортирует roster/rules из read-only manifest. Checksum/version сохраняются под блокировкой; повтор не меняет стоимость, результаты или версии. ScoringRule, опубликованная история и receipts неизменяемы в EF. Замена стоимости в manifest даже с обновлённым checksum отвергается. Миграция не заполняет неполученные результаты нулевыми вердиктами.

`IApplyEvaluation.InitialAsync` — доверенный внутренний порт, без пользовательского маршрута. Он нормализует evaluation, сериализует доступ по checkId, проверяет inbox/receipt до expected=0, затем блокирует snapshot турнира. Один commit сохраняет result/publication/snapshot/receipt/inbox. Повтор с новым messageId возвращает прежние поля receipt; JSONB может менять порядок/пробелы. Противоречащий смысл того же ID отвергается. Другой Initial того же tuple сохраняет Rejected без замены источника. Нет правила/roster — наблюдаемый Deferred без receipt и фиктивного 0. Первичный acknowledgement хранится локально: внешний consumer для Initial не требуется. Runtime broker/outbox и обработка Appeal остаются RES-INT-02 и RES-BE-06.

Публичный GET standings использует Repeatable Read для snapshot/roster/results и один SQL SUM/DENSE_RANK. Pending не содержит score, пустая сумма — "0", равные суммы имеют общее место без дополнительных критериев. DTO не раскрывает solution/material/reviewer/назначения. Авторитетный алгоритм ранжирования только один — SQL; case-наборы RES-UT-02 проверяются на PostgreSQL без второго production алгоритма.

Private team GET проверяет независимым адаптером общий JWT-контракт из [authentication.md](../../../../../contracts/authentication.md) и берёт teamId только из проверенного субъекта. Internal basis принимает отдельные `ServiceIdentity:Issuer`, `ServiceIdentity:Audience`, `ServiceIdentity:PublicKeyPath`: RS256/at+jwt, `token_use=service`, `sub=Appeals`, срок/подпись и точная аудитория. Пользовательский JWT не допускается. Ключ только публичный RSA 3072+, private key в Results не передаётся. При отсутствии service-конфигурации служебное чтение закрыто; выдача credentials потребителю подключается в APL-INT-02. В интеграционных тестах используются независимые user/service ключи и аудитории.

Internal basis читает актуальную опубликованную строку без кэша, сравнивает expectedResultVersion и возвращает 404/409/503. Ответ не выдаёт право подать апелляцию. Private/internal ответы и ошибки имеют private/no-store; публичный снимок — public/max-age=0/must-revalidate и ETag. SSE — следующая RES-BE-05.

Проверки: `pwsh -NoProfile -File scripts/check.ps1`, `node scripts/check-results-storage.mjs` (изолированный tmpfs PostgreSQL, запрет сброса чужой БД, up/down/up, constraints/rollback, concurrent Apply, SQL ranks, настоящий HTTP host с БД/JWT). `node scripts/check-results-http.mjs` проверяет живой Compose/OpenAPI с реальным Checking issuer. Ни один скрипт не пишет оценки через публичный endpoint. Сквозной V1 с браузером и брокером остаётся отдельной приёмкой.
