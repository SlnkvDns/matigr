# Хранение и команды Checking — CHK-BE-02/03/05

Собственная PostgreSQL и EF Core: `CheckingDbContext`, локальные persistence records и миграции `20261023171035_InitialCheckingStorage` / `20261023173153_PreparedFixtureSet`. Domain не зависит от EF. Records не являются контрактами API/брокера. Внутренний bootstrap реализован в CHK-BE-03, HTTP TakeNext/read handlers и отдельные DTO — в CHK-BE-05. Complete/Refuse реализованы в CHK-BE-06; transport workers реализованы в CHK-INT-02.

Схема содержит `fixture_sets`, `solution_references`, `checks`, `assignments`, `reviewer_scopes`, `check_history`, `recheck_request_receipts`, `http_idempotency`, `inbox`, `outbox`, `processing_failures`. Частичные UNIQUE гарантируют один Active на reviewer во всём Checking и один Active на Check; Initial уникален на solution, Appeal — на appealId, reviewRevision — внутри solution. Внешние team/task/result/appeal IDs не имеют межсервисных FK.

`checks.version` — EF concurrency token. При изменении отслеживаемой строки `SaveChanges` увеличивает исходную версию на один; stale update вызывает `DbUpdateConcurrencyException`. Принятый snapshot, основание Check и завершённый Check не изменяются через этот путь записи. Явный SQL обязан сохранять те же условия/CAS. TakeNext использует CAS; Complete/Refuse подключены в CHK-BE-06. Частичные UNIQUE и CHECK не заменяют проверку полномочий и допустимости перехода в Domain/Application.

Локальные FK связывают solution/tournament, check/tournament и scope назначения. Составной `fk_checks_current_assignment` не позволяет сослаться на Assignment другого Check. Он объявлен непосредственно в SQL миграции как `DEFERRABLE INITIALLY DEFERRED`, чтобы Check и его первое назначение можно было вставить в одной транзакции без циклического порядка вставок EF; этот FK проверяется PostgreSQL tests, а не только model snapshot. Completed сохраняет ссылку на своё завершённое назначение; SeniorQueued не имеет текущего назначения. У назначений нет TTL/heartbeat.

`StorageProtection:KeyPath` указывает на постоянный внешний ключ: 32 байта, записанные 64 hex-символами. В Compose используется уже подготовленный `.local/secrets/capability-protection-key`, доступный только Checking и копируемый с mode 600 для UID 1654. Отсутствующий/невалидный ключ останавливает запуск; автоматической ротации нет. `StorageProtection` создаёт случайную 256-битную capability, хранит SHA-256 и AES-256-GCM ciphertext с отдельными nonce/tag. Associated data связывает capability с assignment/reviewer, HTTP-ответ — с subject/operation/key. Полный сохранённый HTTP-ответ шифруется; capability не восстанавливают из hash. CHK-BE-05 проверяет актуального владельца/Active при чтении; Complete/Refuse проверяют capability в CHK-BE-06. Ключ нужно сохранять вместе с восстановлением БД; потеря/подмена обнаруживается ошибкой расшифрования.

Inbox хранит только завершённую обработку по `(consumer,messageId)`; отложенные/невалидные сообщения имеют отдельную диагностику. Outbox сохраняет стабильный messageId/envelope, попытки/следующую попытку/техническую блокировку и статус отправки. Состояния транспорта и поля retry не вводят бизнес-сроков. HTTP/recheck receipts сохраняют исходный hash/ответ; TakeNext сравнивает повтор и записывает результат одной транзакцией; recheck handler остаётся CHK-INT-03. Автоматической очистки receipts нет.

В Local миграция и bootstrap применяются до открытия HTTP; `Storage:ApplyMigrations=false` отключает этот startup adapter для отдельных test hosts. В остальных средах schema применяется явно при deployment. Fixture/material adapter регистрируется только в Local/Test.

CHK-BE-03 добавляет `fixture_sets`: постоянные version/checksum локального набора. `PreparedFixtureBootstrapper` блокирует эту запись и одной транзакцией сохраняет scopes, принятые ссылки и Initial Check/историю. Изменённый набор не импортируется поверх прежнего даже с обновлённым checksum-файлом. Порт `IAcceptedReferenceBootstrap` не является HTTP/API приёма: на неизменяемом SolutionReference `INSERT ON CONFLICT` и блокировка строки сериализуют повтор/конфликт; создание ссылки, Initial Check и истории атомарно. Повтор возвращает прежний Check, включая уже завершённый. Времена входного снимка канонизируются до микросекунд PostgreSQL. Без истории загрузки, QR, producer/consumer SolutionAccepted или проверки текущей активности турнира.

`PreparedMaterialStore` реализует `IReadOnlyMaterialStore` по полному снимку и allowlist проверенного manifest. Разрешённый fixture file проверяется на reparse/symlink и SHA-256 при каждом чтении; возвращается read-only MemoryStream проверенных байтов. Внешние path/URL не интерпретируются. Ошибки материала не пишут в БД и не создают вердикт; HTTP-маршрут и проверка актуального владельца подключены в CHK-BE-05.

Проверки из корня репозитория:

```powershell
pwsh -NoProfile -File scripts/check.ps1 -Restore
node scripts/check-checking-storage.mjs
```

Вторая команда требует Docker и подготовленный ключ (`node scripts/prepare-fixtures.mjs`). Она создаёт отдельный проект `matigr-checking-storage-tests` без host ports и без постоянного volume: PostgreSQL 18.6 в tmpfs, собственные тестовые credentials/сеть. Tests отказываются сбрасывать БД с именем, отличным от `checking_storage_test`. Проверяются up/down/up миграции, UNIQUE/CHECK/FK, реальное ожидание конкурирующей транзакции/commit/rollback, CAS, атомарный rollback связанных записей, освобождение после отказа и persistence шифрованных ответов. Затем отдельный контейнер/процесс читает прежний checkpoint с прежним ключом. `finally` удаляет только этот тестовый Compose. Существующие `matigr` volumes не используются. CI запускает ту же команду.

CHK-BE-05: `CheckingWork` проверяет JWT subject/role/tournament и локальный scope. TakeNext в одной транзакции берёт advisory mutex reviewer во всём сервисе, ищет receipt до проверки занятости, выбирает очередь через `FOR UPDATE SKIP LOCKED`, сохраняет Assignment, CAS Check, историю и зашифрованный ответ. Ограниченный повтор после rollback разрешает известный конфликт UNIQUE/CAS/serialization. Mutex не является TTL назначения.

Ключ HTTP хранится как SHA-256 представление для индекса PostgreSQL без нового ограничения длины входного ключа; hash нормализованного тела хранится отдельно. Повтор восстанавливает исходные 200/204/409, ETag/capability/correlationId; другое тело возвращает IdempotencyConflict. GET текущего назначения глобален, сохраняет assignment/capability после restart и не скрывает занятую работу фильтром турнира. Очередь использует keyset cursor по createdAt/checkId, связанный с турниром/очередью; `Checking:QueuePageSize` по умолчанию 50 — техническая настройка.

Материал проверяет текущего владельца и Active до/после IO, без SQL-транзакции во время чтения. При потере назначения поток закрывается; отсутствие/подмена материала даёт 503 MaterialUnavailable без вердикта. Ответ private/no-store, минимальные queue/Check DTO не содержат capability/materialRef. Возможность Senior работать в общей очереди отражена второй строкой Reviewer scope: четыре строки для трёх субъектов, без изменения manifest.

Взятие SeniorQueued Appeal сохраняет RecheckAssigned в outbox той же транзакцией, сохраняя прежнюю базу/selected reviewer/escalation. Публикация outbox реализована в CHK-INT-02; HandleRecheckRequested остаётся CHK-INT-03. Новая миграция не требуется.

Проверки хранения/команд CHK-BE-02/03/05 включают настоящую конкурентность, replay пустого/busy ответа, rollback при сбое записи receipt и потерю владельца во время IO. Реальный HTTP smoke описан в [корневом README](../../../../../../README.md). CHK-IT-01 и broker/E2E задачи остаются открытыми до выполнения их зависимостей и полного набора сценариев.

CHK-BE-06 реализует Complete/Refuse: mutex reviewer → lock Check → проверка subject/scope/assignment/capability → успешный receipt до stale If-Match → доменный переход → assignment/history/CAS/receipt/outbox одним commit. Отказ обычного Initial не требует внешнего события; Appeal отказ пишет RecheckEscalated. Завершение обоих kind пишет CheckCompleted. После commit жюри свободен, Results ждать не нужно; старый token не разрешает новое действие/материал, успешный replay не возобновляет работу. Конкурентные Complete/Refuse имеют одного победителя. Реальные HTTP/outbox schemas проверяет check-checking-transitions.mjs; CHK-IT-02 завершена на настоящем HTTP/PostgreSQL; CHK-IT-04 требует полного crash/fault-набора.

CHK-IT-02 проверяет гонки HTTP с реальной PostgreSQL, restart host при активном назначении, прежний capability/credential и ошибки материала без вердикта. CHK-FE-04 перечитывает назначение при focus/pageshow/online/возврате вкладки; BroadcastChannel передаёт только invalidation без приватных данных. Старые read/material ответы отменяются, replay команды не используется как актуальное назначение, 409/412 вызывают GET без автоматической новой команды. Нет таймера освобождения.

CHK-INT-03 подключает `RecheckRequests`: semantic hash/request receipt до состояния, общий reviewer mutex с TakeNext, lock принятой ссылки для revision, проверка completed non-senior базы, scope и точного материала. Busy не создаёт Check; после подтверждённого busy новый ручной request может назначить того же/другого свободного жюри. Assigned/Rejected/inbox/outbox фиксируются с локальным переходом. Повтор успешного Appeal не меняет selected/request/assignment и не создаёт вторую проверку. Передача использует прежние Complete/Refuse/Senior handlers. Текущий storage/HTTP набор: 44 tests + checkpoint, CHK-IT-04 и браузерные V1/V2 приняты; полный Appeal broker gate — CHK-IT-03.
