# 002 — Результаты команд и онлайн-таблица

Статус: **одобрена пользователем 23 октября 2026 года** вместе со спецификациями 001 и 003. Планы/задачи затем одобрены и реализация поручена отдельно в тот же день; первоначальный MVP завершён. Явно открытые вопросы и технические варианты сохраняют свой статус. Основания: [диаграмма](../../event-storming/tournament.mmd), [архитектура и Qxx](../../architecture/architecture.md), [контракты](../../architecture/event-contracts.md). Зависимости: [Checking](../001-checking/spec.md), [Appeals](../003-appeals/spec.md).

## 1. Назначение и границы

Results преобразует сохранённые вердикты Checking в авторитетный результат команды по задаче, предоставляет результаты команды и онлайн-таблицу, применяет итоги перепроверки и сохраняет историю. Исходная модель: A8; C20/C21; E21/E22; P7; RM4–RM6. Публикация результата нужна для P8; по согласованному D06/Q01 она происходит автоматически после обработки вердикта Results, без отдельного подтверждения.

Вне границ: назначение жюри, изменение вынесенного вердикта, принятие апелляции, управление задачами/командами/турниром. Results не определяет самостоятельно, что команда опоздала с апелляцией; он предоставляет доверенные сведения о публикации.

Согласовано пользователем 23 октября 2026 года (D01/Q03): команда не отправляет решение задачи повторно. Result относится к единственному Solution данного tournamentId/teamId/taskId. Передача старшему и апелляция оценивают тот же материал. D13 разрешает одну апелляцию команды на задачу; D14 запрещает апелляцию на финальный вердикт старшего после обычной передачи.

### Дополнительные согласованные правила результатов

- D06 / Q01: первичный результат и изменение после апелляции публикуются автоматически после обработки вердикта Results. Ручного утверждения/отложенной публикации в MVP нет. Это не означает публикацию до доставки и обработки события Checking.
- D07 и D09 / часть Q09: итог команды — сумма баллов по задачам. Команды с одинаковой суммой делят место; дополнительные критерии для разрешения равенства не используются. Согласована нумерация без пропусков: 1, 1, 2. Место равно одному плюс число различных сумм, превышающих сумму команды.
- D08 / часть Q16: все команды видят общую таблицу с баллами каждой команды по задачам. Эта же таблица доступна посетителю без входа. Публичность не распространяется автоматически на материалы, внутреннюю историю, авторство проверок и детали апелляций.
- D16/D17: организатор завершает вручную, но вовремя поданные апелляции можно брать и заканчивать после конца. Results продолжает автоматически публиковать их итоги и пересчитывать таблицу; конец не замораживает её окончательно.
- D18–D20: при отказе апелляционного жюри итог выносит старший на том же Check; уже принятые первичные решения также обрабатываются после конца. Комментарии жюри к вердиктам не нужны. Results сохраняет фактическую цепочку назначения в receipt, а не требует неизменного исполнителя.
- D22: стоимость задач задана заранее в тестовых данных и не меняется в ходе турнира. D23: временный локальный вход под фиксированными субъектами должен заменяться полноценной регистрацией; D24: загрузки/приёма в текущем приложении нет, Results начинает с вердиктов по уже принятому решению.

## 2. Пользователи и чтение

- Команда читает собственные результаты и общую таблицу с баллами всех команд по задачам (RM4/RM5).
- Посетитель без входа читает общую таблицу, баллы по задачам, суммы и общие места (D08).
- Организатор читает результаты в согласованном объёме (RM6), без редактирования турнира.
- Appeals получает опубликованное основание и версию через служебный API.
- Видимость внутренней истории, сведений о жюри/апелляциях и технических ошибок ещё Q16. Комментариев жюри в MVP нет (D20). Для публичной таблицы вход не требуется ни на странице, ни в API/канале обновлений.

Жюри сохраняет вердикт через Checking, а не прямой записью score в Results. Универсальный endpoint ручного редактирования баллов в MVP не предлагается.

## 3. Модель и владение

| Объект | Предлагаемые данные и назначение |
| --- | --- |
| TeamTaskResult | resultId; уникальный tournamentId/teamId/taskId; solutionId/materialVersionId и исходный checkId; outcome/decisionOrigin; score; scoring rule/version; resultVersion |
| Публикация | publicationId, resultId/resultVersion, снимок/decisionOrigin и publishedAt; история не исчезает при коррекции. Results не владеет фактом ручного конца или окном допуска Appeals |
| Evaluation receipt | checkId, фактические reviewerId/assignmentId/evaluationDecisionOrigin, для Appeal — selectedReviewerId, при передаче — escalationId; основание версии, исход обработки, итог/баллы, appealId/requestId. Дедупликация по checkId; no-op не меняет источник прежней публикации |
| История результата | Предыдущее и новое значения, связь с проверкой/апелляцией, авторство вердикта и время фиксации; не требует Event Sourcing |
| TeamResults / Standings | Локальные модели чтения/запросы из собственных данных Results; не отдельные сервисы |
| Scoring fixture | По D22 стоимость задана заранее и фиксирована в ходе турнира; в MVP согласованный набор тестовых данных с версией. Будущий источник — турнирный контекст вне объёма |

`resultVersion` описывает актуальную бизнес-версию результата, не schemaVersion и не aggregateVersion чужой проверки. При подтверждении без изменения предлагается отдельный receipt без изменения опубликованного основания и его source checkId; если изменяется авторитетное основание, это уже новая версия. Этот выбор должен остаться последовательным во всех API и контрактах.

### Правила баллов

**Подтверждено P7:** Correct даёт полную стоимость задания, Incorrect даёт 0. Частичные баллы не вводятся. Отсутствующий результат означает «не проверено/нет результата», а не Incorrect и не доказанный нулевой результат.

**Согласовано D06/D07:** итог команды — сумма баллов по задачам; таблица строится по автоматически опубликованным результатам. Равные суммы дают общее место, без дополнительных критериев. Неопубликованного обработанного результата в нормальном процессе MVP нет. До обработки вердикта отсутствие результата сохраняет отдельный статус и не превращается в Incorrect.

D22 определил источник MVP (тестовые данные) и неизменность стоимости в ходе турнира; функции изменения стоимости/пересчёта из-за неё нет. Q09 уточнён при одобрении плана (pending отдельно, пустая сумма=0), затем явно пользователем при реализации 23 октября: тестовые задачи 10 и 20 целых баллов, точные числа JSON строками. [Профиль v1](../../architecture/runtime-baseline.md) относится только к локальным fixtures. Версия набора служит обнаружению несовпадения среды/восстановления, не разрешает менять стоимость. Общие места/1, 1, 2 согласованы; штрафов/тай-брейков нет. Технический порядок равных строк не меняет их место.

## 4. Инварианты и версии

1. В Results не более одного актуального TeamTaskResult на tournamentId/teamId/taskId и единственный связанный принятый Solution по D01. Чужой/новый solutionId для уже занятого ключа не выбирается вместо прежнего как новая отправка.
2. Вердикт применяется по достоверному событию Checking, баллы вычисляются Results по известной версии правила, а не принимаются из браузера/Appeals.
3. Первая оценка создаёт результат только при его отсутствии (`expectedResultVersion=0`). Если он существует, повтор того же checkId идемпотентен; другой первичный Check/solutionId — конфликт целостности, а не разрешённая повторная отправка. Изменение по апелляции идёт отдельным условным переходом по версии.
4. Перепроверка применима только к указанным resultId, ключу, материалу, опубликованному основанию/baseCheckId и expectedResultVersion. Случайная последняя доставка не выигрывает.
5. Применённый checkId учитывается один раз. Сначала проверяется receipt, затем CAS: повтор уже применённого сообщения не должен стать ложным конфликтом версии.
6. Изменение результата заменяет вклад задачи. Ни повтор, ни апелляция не добавляют этот вклад повторно.
7. Изменённая бизнес-версия, история, receipt, inbox, согласованные локальные модели чтения и outbox-подтверждение фиксируются одной транзакцией. При no-op фиксируются receipt/inbox/outbox, а published resultVersion может не изменяться.
8. Недостаток scoring rule или зависимостей не приводит к тихому начислению 0. Нужен наблюдаемый статус ожидания/ошибки и восстановление.
9. PublishedAt — время бизнес-публикации в Results, не время вердикта Checking и не время открытия страницы. Срок подачи не пересчитывается из времени доставки события.
10. Публикация нового/изменённого результата, его сумма и доступный снимок таблицы фиксируются согласованно с бизнес-версией. Нельзя подтвердить применённую коррекцию, оставив её недоступной из-за отдельного ручного шага.
11. Равные суммы всегда дают равные места, следующая отличная сумма получает следующий номер без пропуска (1, 1, 2). Изменение результата может переместить несколько команд; пересчёт мест не ограничивается строкой одной команды.
12. Публичное чтение таблицы не требует удостоверения. Публичный DTO/канал содержит только согласованные поля таблицы; не предоставляет доступ к материалу, служебному снимку Appeals, назначению или командам изменения.
13. Results хранит происхождение вердикта и цепочку фактического назначения из Checking. SeniorEscalation допустим и при kind=Appeal после D18; запрет новой апелляции на старшего не запрещает применение его итога уже существующей. Receipt копирует selectedReviewerId/фактического reviewerId/assignmentId/escalationId для корреляции, в том числе при no-op; происхождение прежней публикации при этом не подменяется. Комментарий к вердикту не нужен.

## 5. Процессы

### RS-01. Первичная фиксация

Results получает `CheckCompleted(kind=Initial)`, проверяет схему, отправителя, ключ/материал, известность scoring rule и receipt. В одной транзакции создаёт отсутствующий результат, рассчитывает баллы P7, фиксирует историю и автоматически публикует результат с доступным согласованным снимком. После коммита может отправить `ResultEvaluationApplied`; бизнес-факт соответствует E21.

При недоступном брокере Checking продолжает хранить outbox; до получения события таблица может отставать. UI не показывает «неправильно» по одному отсутствию события. При неизвестной задаче правило не выбирается по совпадению названия; проблема сохраняется для повторной обработки/разбора.

### RS-02. Публикация и чтение

По согласованному D06/Q01 результат автоматически публикуется при успешной обработке оценки Results. Отдельной команды утверждения нет. Такое же правило действует для изменённого результата после апелляции. До обработки события Checking клиент может видеть ожидание; после коммита Results результат доступен через публичное чтение таблицы.

Опубликованный снимок получает publicationId, resultVersion и publishedAt. Команда видит результат, авторитетный score и доступный статус. Appeals получает историческое основание, включая decisionOrigin. Подтверждение без изменения сохраняет исходную публикацию/время; технический повтор не публикует заново. Коррекция создаёт новую опубликованную версию, но D13 не разрешает новую апелляцию на неё; D10 также не создаёт новый интервал от публикации.

### RS-03. Онлайн-таблица

Клиент, включая посетителя без входа, загружает снимок общей таблицы через публичный API. Снимок содержит идентификатор/версию представления и время формирования; для каждой команды — идентификатор/отображаемое название, баллы по задачам, сумму и место. Баллы и итог берутся из согласованного локального состояния Results; общие места нумеруются без пропусков по различным суммам (D09). По одобренному плану незавершённая задача имеет отдельный pending status без score, пустая сумма=0; дополнительные публичные поля — остаток Q16.

Предлагаемый канал обновлений сообщает о необходимости перечитать данные/новой версии. Дубли уведомлений безопасны. После разрыва клиент перечитывает снимок; наличие WebSocket не является гарантией полноты. Если используется схема snapshot+subscribe, нельзя пропустить изменение в промежутке: нужен повторный снимок после установления подписки либо согласованный cursor/resume. Механизм и допустимая задержка — Q10.

### RS-04. Применение апелляционной оценки

Results получает `CheckCompleted(kind=Appeal)`. После дедупликации проверяет expectedResultVersion и основание. Если вердикт изменяет результат, создаёт следующую бизнес-версию и заменяет баллы задачи (E22). Если подтверждает прежний результат, регистрирует receipt без повторного начисления; подтверждение всё равно отправляется.

В обоих случаях `ResultEvaluationApplied` содержит checkId, appealId, requestId, исходную и итоговую версии, score, changed и сведения о публикации. По D06 коррекция сразу публикуется: подтверждение означает доступность итогового снимка. Дополнительный шаг публикации/контракт ожидания не нужен. При подтверждении без изменения receipt ссылается на существующую доступную публикацию.

### RS-05. Устаревшее основание

Если resultVersion/baseCheckId уже не соответствует основанию апелляции, действующий результат сохраняется. Формируется receipt конфликта и `ResultEvaluationRejected`. Полученный вердикт Checking остаётся в его истории, но не становится баллами автоматически. Повтор с новым expectedResultVersion без нового бизнес-решения запрещён предложенной защитой. Дальнейший ход апелляции — Q15.

## 6. Предлагаемая поверхность API и интерфейс

| Возможность | Ответ | Замечание |
| --- | --- | --- |
| Результаты команды в турнире | Задачи, статусы, опубликованные score/outcome, версии и итог по согласованному правилу | Команда не получает чужие приватные сведения |
| Таблица турнира | Команды, баллы по каждой задаче, сумма, общее место, snapshotVersion/generatedAt | Без входа; равные суммы делят место, нумерация без пропусков: 1, 1, 2 |
| Деталь результата | Опубликованный результат и доступная история | Не вся внутренняя история автоматически публична |
| Служебный снимок для Appeals | resultId/version, solution/material/baseCheck, decisionOrigin, publicationId/publishedAt | SeniorEscalation запрещает подачу D14; квота и ручное закрытие подачи принадлежат границе допуска Appeals, не выводятся из публикации Results |
| Изменения таблицы | Версия/инвалидация или согласованный push-формат публичных полей | Доступны без входа в том же публичном scope; после reconnect повторное чтение. Приватные сведения этим каналом не передаются |

Frontend показывает раздельно «не проверено», «вердикт сохранён/результат ожидается», «опубликован» и «апелляция в процессе», если соответствующие сведения доступны. Состояния из разных сервисов не выдаются за один атомарный снимок. Не начислять баллы оптимистически в браузере; можно показать локальный индикатор ожидающего обновления.

## 7. Проверяемые критерии приёмки

| ID | Дано / действие | Ожидаемый результат |
| --- | --- | --- |
| RS-A01 | Вердикт Correct, стоимость задачи задана фикстурой | Score равен стоимости именно этой версии задачи |
| RS-A02 | Вердикт Incorrect | Score=0 и статус отрицательного результата |
| RS-A03 | Вердикт ещё не получен | Состояние отсутствия/ожидания, не ложный Incorrect |
| RS-A04 | Один checkId доставлен повторно, в том числе с новым messageId | Один вклад и прежнее подтверждение, без новой версии из-за дубля |
| RS-A05 | Два обработчика создают результат одного ключа | Одна актуальная запись; дубль безопасен, несовместимая вторая оценка — явный конфликт |
| RS-A06 | Апелляционная оценка изменяет вердикт при актуальной базе | Новая версия, замена score задачи, согласованное обновление команды/таблицы и подтверждение |
| RS-A07 | Перепроверка подтверждает прежний вердикт | Сумма не увеличивается, receipt и подтверждение имеются |
| RS-A08 | Устаревшая перепроверка доставлена после новой версии | Новая версия не перезаписана, Appeals получает конфликт |
| RS-A09 | Сбой до/после транзакционного коммита | Нет частично обновлённых результата/receipt/проекции; после восстановления возможна безопасная повторная доставка |
| RS-A10 | Scoring rule отсутствует | Ошибка/ожидание видны, 0 по умолчанию не начисляется |
| RS-A11 | Клиент пропустил push или переподключился | Повторный снимок возвращает актуальные доступные значения без двойного учёта |
| RS-A12 | Между snapshot и subscribe произошла коррекция | Повторный снимок/cursor устраняет пропуск, UI не остаётся навсегда на старой версии |
| RS-A13 | Историческая публикация после коррекции запрошена Appeals | Возвращается исходное основание/время; срок не начинается заново от чтения |
| RS-A14 | Таблица и данные команды прочитаны для одной версии после применения | Значения задачи и итог согласуются по принятому правилу подсчёта |
| RS-A15 | Для существующего ключа результата пришёл другой solutionId как первичная оценка | Прежний результат не заменяется; нарушение запрета повторной отправки наблюдаемо |
| RS-A16 | Первичный вердикт успешно обработан Results | Результат автоматически доступен в таблице без ручного подтверждения |
| RS-A17 | Апелляционная коррекция успешно применена | Новая версия автоматически опубликована, подтверждение не опережает доступный снимок |
