# 001 — Проверка решений

Статус: **одобрена пользователем 23 октября 2026 года** вместе со спецификациями 002 и 003. Планы/задачи затем одобрены и реализация поручена отдельно в тот же день; первоначальный MVP завершён. Явно открытые вопросы и технические варианты сохраняют свой статус. Источники: [полная диаграмма](../../event-storming/tournament.mmd), [архитектура и Qxx](../../architecture/architecture.md), [контракты](../../architecture/event-contracts.md). Связанные процессы: [результаты](../002-results/spec.md), [апелляции](../003-appeals/spec.md).

## 1. Назначение и границы

Член жюри видит доступные ему решения, получает одно свободное задание на проверку, читает материал и выносит вердикт либо отказывается с передачей старшему. Checking также исполняет перепроверки, запрошенные Appeals. Вердикт передаётся Results; Checking не начисляет баллы.

По окончательному уточнению D24 загрузка/приём решений вообще не входят в текущий объём. Checking начинает с уже принятого и идентифицированного решения. Для локального теста используются подготовленные метаданные/материалы; ни формы загрузки, ни фотографирования, ни ручного выбора задачи, ни QR-декодера нет. Регистрация турнира/бланки/вопросы также исключены.

Подтверждённая основа: A7; C15–C19; E16–E20; P5/P6; RM2/RM3; выполнение C24–C26 для апелляций. A6, C10–C14, E10–E15 и RM1 принадлежат внешнему приёму, который не реализуется. E13 задаёт смысл входной границы уже принятого решения; будущий SolutionAccepted контракт/тестовый bootstrap описаны отдельно от его производителя.

### Уточнения, согласованные пользователем 23 октября 2026 года

- Для команды по задаче турнира допускается одна отправка решения. Повторная бизнес-отправка запрещена; технический повтор уже принятого запроса возвращает прежний результат. Апелляция проверяет тот же материал и не является новой отправкой.
- Каждый член жюри может проверять любую задачу; закрепления за отдельными задачами нет. У члена жюри не более одной незавершённой проверки. После завершения предыдущей он может взять следующую, если свободен.
- После отказа обычного проверяющего окончательный вердикт выносит старшее жюри. Если старший сейчас не может проверять, решение ожидает в его очереди; обычному жюри оно обратно не передаётся как способ разрешения отказа.
- После успешной передачи отказной работы в очередь старшего обычный проверяющий сразу освобождается и может брать следующую задачу, не ожидая вердикта старшего.
- Закрытие страницы/вкладки и потеря связи не снимают назначение. При возвращении проверяющий продолжает ту же работу; до её завершения либо успешной передачи старшему новую работу взять нельзя. Автоматическое освобождение из-за отсутствия связи или по таймауту не вводится.
- D12: выбравший апелляцию член жюри сам перепроверяет решение с тем же лимитом занятости. D13: одна апелляция команды на задачу турнира. D14: вердикт старшего после обычной передачи нельзя обжаловать.
- D15: апелляцию может выбрать первоначальный проверяющий. D16: турнир завершает организатор вручную. D17: вовремя поданную апелляцию можно назначать/завершать после конца; закрытие новой подачи не блокирует её Checking-процесс.
- D18: отказ от назначенной апелляционной проверки передаёт тот же Check старшему и освобождает отказавшегося; новая апелляция/второй Check не создаются. D19: принятые до конца первичные решения также можно брать/завершать после конца. D20: комментарии жюри к любому вердикту не нужны.
- D21/D24: фото листа с QR — будущий внешний сценарий, весь приём исключён. D22: стоимость задач фиксирована заранее. D23: локальный переключатель тестовых субъектов подходит, но должен заменяться полноценной регистрацией без смены внутренних ID/бизнес-правил.

После поэтапного разбора пользователь одобрил спецификацию в целом 23 октября 2026 года. D14 уточнил окончательность вердикта старшего запретом апелляции. Отмеченные открытыми условия/полномочия ручного освобождения зависшего назначения Q06 не получают произвольного ответа из самого факта одобрения.

## 2. Участники и полномочия

| Участник | Возможность | Что ещё нужно согласовать |
| --- | --- | --- |
| Команда | В этой спецификации не загружает/не идентифицирует решение; результат/апелляция — соседние спецификации | Приём целиком вне объёма D24 |
| Тестовый bootstrap / будущий внешний источник | Передать уже принятый снимок для создания очереди | Без user-facing intake API и без реализации производителя SolutionAccepted |
| Член жюри | Проверять любую задачу в доступном турнире, иметь одну незавершённую проверку, продолжать её после возвращения; брать следующую после завершения или передачи старшему | Доступ к турнирам — остаток Q05; ручное освобождение зависшей работы — остаток Q06 |
| Старшее жюри | Брать переданные решения из своей очереди и выносить окончательный вердикт | Назначение конкретного старшего при нескольких старших и его участие в апелляциях — остаток Q05 |
| Appeals | Запросить перепроверку по принятой апелляции | Отдельная межсервисная аутентификация, не пользовательский role header |

Backend проверяет субъект, турнир/команду, роль, принадлежность материала и действительность назначения. Произвольный userId в теле запроса не назначает проверяющего.

## 3. Данные и модель

Предложение модели:

- `SolutionReference`: локальный неизменяемый снимок уже принятого внешнего решения: solutionId, tournamentId/teamId/taskId, materialVersionId/materialRef, acceptedAt и версия источника. Не является агрегатом подачи A6 и не принимает файлы. Подготовленный материал доступен жюри на чтение. D01 — предпосылка одного внешнего решения по ключу; локальные ограничения выявляют нарушение, не реализуют сам процесс отправки.
- `Check`: checkId, solutionId/materialVersionId, kind Initial/Appeal, состояние, назначения, бинарный outcome без комментария, версия/история и decisionOrigin. OrdinaryReview — обычная первичная оценка, AppealReview — оценка выбравшего апелляцию, SeniorEscalation — финальная оценка старшего после отказа в любом kind. Для Appeal сохраняются selectedReviewerId исходного выбора, appealId/recheckRequestId, baseCheckId и основание результата. Current reviewerId/assignmentId меняются при передаче; escalationId связывает её историю. Личный старт назначается атомарно, передача старшему не создаёт новый Check.
- `Assignment`: идентификатор/token назначения и reviewerId; не отдельный сервис. Назначение и занятость хранятся в PostgreSQL, а не только в браузере или памяти процесса. Старый token недействителен после отказа/согласованного переназначения. При возвращении клиент получает актуальные назначение и версию с backend, не восстанавливает полномочия из устаревшего локального состояния.
- `reviewRevision`: номер рассмотрения в пределах solutionId; не версия результата и не правило выбора нескольких отправок.

Один материал может участвовать в первичной проверке и последующих перепроверках; каждая завершённая проверка остаётся отдельным историческим фактом. Принятый первичный вердикт не редактируется для реализации апелляции.

### Предлагаемые состояния Check

| Состояние | Допустимый переход | Основание |
| --- | --- | --- |
| Queued | Assigned | Атомарное взятие свободным уполномоченным жюри без другой незавершённой проверки |
| Assigned | Completed | Вердикт Correct/Incorrect актуальным владельцем |
| Assigned | SeniorQueued | Отказ, передача старшему и освобождение обычного жюри в одной транзакции |
| SeniorQueued | SeniorAssigned | Взятие свободным старшим; пока он занят/недоступен, работа остаётся SeniorQueued |
| SeniorAssigned | Completed | Окончательный вердикт старшего по переданной проверке |
| Completed | Нет повторного завершения | Только новая перепроверка отдельным Check |

По D12 начальное назначение апелляции — сразу Assigned на свободного выбравшего; ReviewerBusy не создаёт Check. D18 разрешает Assigned → SeniorQueued → SeniorAssigned → Completed внутри того же Appeal Check. Переход снимает прежний token/занятость; старший берёт работу при возможности с общим лимитом. Kind и исходный selectedReviewerId сохраняются, фактический исполнитель/assignmentId меняются, история связывается escalationId. Первоначальный жюри допустим D15, работа после конца разрешена D17/D19. Ручное освобождение зависшего назначения ещё Q06.

## 4. Инварианты

**Из диаграммы:** свободная проверка отдаётся одному проверяющему (P5); отказ ведёт к старшему (P6); возможны положительный и отрицательный вердикты (E17/E18); перепроверка использует тот же A7.

**Дополнительно согласовано пользователем:** уникальность отправки по tournamentId/teamId/taskId; любая задача доступна каждому жюри в разрешённом турнире; у одного reviewerId не более одного активного назначения. Ограничение занятости проверяющего едино для общей/старшей очередей и назначенных ему перепроверок, а не независимо на каждой вкладке. После отказа финальную оценку переданной работы выносит старший.

**Предлагаемые технические ограничения:**

1. На Check не более одного актуального назначения. Проверка очереди и её захват — одна локальная транзакция; читательская проекция не разрешает захват.
2. Только актуальный уполномоченный владелец может завершить назначение; команда содержит ожидаемую версию и token. Состязание завершения и отказа даёт один успешный переход.
3. Уже принятое внешнее решение создаёт не более одного первичного Check. Повтор входного факта/тестового bootstrap идемпотентен по solutionId и ключу команды/задачи/турнира; это не приём от пользователя.
4. Один appealId создаёт не более одной перепроверки. Повтор транспортного запроса возвращает тот же checkId.
5. Вердикт и outbox `CheckCompleted` фиксируются вместе; изменение очередей и отказ — вместе.
6. Completed неизменяем; противоречащий повтор — конфликт. Структурированная история reviewerId/времени/версий/передач сохраняется, её публичность — Q16; текстового комментария жюри нет.

7. Предлагаемая защита согласованного лимита: уникальное активное назначение по reviewerId в PostgreSQL и атомарная проверка занятости вместе с захватом Check. Два разных Check не могут одновременно достаться одному проверяющему даже из разных вкладок/очередей. Блокировки одной строки Check для этого недостаточно.
8. Локальный SolutionReference уникален по solutionId и ключу команды/задачи/турнира. Несовместимый второй solutionId от источника не подменяет снимок и не создаёт вторую первичную проверку. Идентичный повтор безопасен; это защита входного контракта, не API запрета отправки командой.
9. Отказ завершает назначение обычного жюри и освобождает его занятость в той же транзакции, которая помещает работу в SeniorQueued. После коммита он может брать следующую работу. Ожидание/занятость старшего этому не препятствуют.
10. Разрыв клиентского соединения не освобождает занятость и не создаёт отказа или вердикта. Возобновление использует сохранённые checkId/assignmentId и актуальное серверное состояние; повторный вход или другая вкладка не создают второе назначение. Возобновление назначения не означает автоматического сохранения неотправленных полей формы — такое требование не согласовано.
11. Отказ апелляционного жюри атомарно сохраняет SeniorQueued, escalationId, снятие назначения/занятости и outbox RecheckEscalated. Взятие старшим создаёт новое назначение на том же Check и подтверждает его Appeals. Завершить старым token нельзя; отказ/вердикт допускают один состязающийся переход.
12. Ни первичный, ни апелляционный вердикт не требует комментария жюри (D20). Аудит автора/версии/передачи и технические reasonCode не являются текстовым комментарием к оценке.

Бизнес-регламент FIFO/приоритетов не задан; технический выбор createdAt/ID принят в T08 и реализован; бинарная оценка без комментария следует P7/D20. Отказ апелляционного жюри передаёт старшему. Лимит/начальное назначение/допуск первоначального заданы. Автоматического timeout нет; ручное вмешательство — Q06. P4 относится к внешнему приёму и не проверяется Checking для уже принятого входа, даже если он доставлен после конца (D19/D24).

## 5. Основные сценарии

### CH-01. Начальное состояние из уже принятого решения

Условие: подготовлены идентифицированное принятое решение и доступный на чтение материал, согласованные ID турнира/команды/задачи. Тестовый bootstrap (в будущем внешний SolutionAccepted) даёт снимок с solutionId/materialVersionId/materialRef/acceptedAt. Checking валидирует целостность ссылок, локально атомарно создаёт SolutionReference и первичный Queued Check. Повтор не дублирует Check; противоречащий снимок изолируется как ошибка входа.

Результат: один локальный снимок и один первичный Check, готовый к жюри. В этом сценарии нет пользовательской отправки, RM1 статусов загрузки, распознавания/ручной привязки задачи, записи файлов или уборки загрузок. Источник принятия/исходного материала — за границей объёма; фикстуры не публикуют фиктивные QR-факты. Инициализация доступна только тестовой среде, не обычным пользовательским ролям.

### CH-02. Взятие и завершение

Условие: доступен Queued Check, пользователь имеет право на эту очередь и не занят другой проверкой. Любая задача допустима без закрепления по предметным задачам. Проверка занятости reviewerId и закрепление Check выполняются атомарно; два одновременных запроса одного жюри не берут две разные работы. Успех возвращает материал, checkId, версию и token; отсутствие доступных записей — явный пустой результат, занятость — явный отказ в новом назначении. Это разные исходы. Повтор прежнего idempotency key возвращает прежнее назначение.

Проверяющий отправляет Correct или Incorrect. Сервис проверяет назначение/версию, завершает проверку, освобождает его занятость и сохраняет исходящее событие одной транзакцией. После этого жюри может взять следующую работу, не ожидая начисления баллов Results. UI сообщает «вердикт сохранён»; до обработки Results нельзя обещать начисление или публикацию.

### CH-03. Отказ и старшее жюри

Условие: актуальное Assigned назначение. Отказ снимает его, освобождает обычного жюри, сохраняет E19 и переводит проверку в SeniorQueued с E20 в одной транзакции. После её коммита обычный жюри может брать следующую работу, даже если старший ещё занят. Простой возврат в общую очередь не соответствует P6. Старший видит RM3, берёт работу при возможности с тем же лимитом одной незавершённой проверки и выносит окончательный вердикт. Пока он занят/не может приступить, решение остаётся в очереди без активного назначения на него; очередь не нарушает лимит назначений. Отказ не превращается в Incorrect/0.

### CH-04. Перепроверка

Условие: доверенный RecheckRequested после ручного выбора с appealId, опубликованным основанием и requestedReviewerId выбравшего жюри. Checking проверяет материал/baseCheckId, в том числе отсутствие запрещённого SeniorEscalation в базе, дедуплицирует попытку/appeal и атомарно проверяет занятость, создаёт Check и назначает именно ему. RecheckAssigned подтверждает персональное назначение, не просто очередь. Жюри исполняет проверку, не меняя материал/базовый Check.

Предложение: ReviewerBusy не создаёт Check; ответ привязан к ID попытки. После такого подтверждённого отказа Appeals может разрешить новый выбор в рамках того же Appeal. Технический повтор старой попытки возвращает её сохранённый исход, не пересчитывая занятость задним числом; повтор успешного запроса возвращает прежний Check/назначение. Новая попытка не допускает двух успешных Check на appealId. Недопустимые связи/противоречивый повтор не исправляются новым ID запроса. Подробный протокол — в контрактах.

Результат: `CheckCompleted(kind=Appeal)` содержит основание версии результата. Совпадение вердикта с прежним не отменяет событие: Results должен подтвердить обработку неизменного результата. Недопустимый запрос даёт явный отказ; технический сбой — повтор, подробности в контрактах.

RequestedReviewerId может совпадать с автором baseCheck (D15). Ручной конец не препятствует назначению/повтору/возобновлению/передаче/завершению ранее поданного (D17/D18), а D19 разрешает брать и завершать уже принятые первичные решения после конца. Своевременный допуск апелляции принадлежит Appeals. При отказе апелляционного жюри тот же Check переходит SeniorQueued с RecheckEscalated; старшему создаётся новое назначение, итог сохраняет kind=Appeal и decisionOrigin=SeniorEscalation. Комментария к outcome нет.

### CH-05. Возвращение после закрытия страницы или потери связи

Условие: у проверяющего есть Assigned/SeniorAssigned назначение. Отключение клиента ничего не меняет в бизнес-состоянии. После повторного открытия страницы/входа frontend запрашивает своё текущее назначение и показывает тот же Check и материал. Занятость остаётся занятой; запрос новой работы другим idempotency key не обходит лимит.

Если команда завершения/отказа успела сохраниться, но ответ потерян, при возвращении показывается актуальное состояние backend: закрытая работа не открывается заново, переданная старшему не возвращается обычному жюри. Повтор прежней команды идемпотентен. Восстановление после перезапуска API использует БД. Политика длительно зависшего назначения с ручным вмешательством пока не согласована (остаток Q06).

## 6. Предлагаемая поверхность API

Это перечень возможностей, а не утверждённые пути/DTO:

| Операция | Вход/выход | Ограничения |
| --- | --- | --- |
| Читать общую/старшую очередь | Разрешённый scope → список/наличие работы | Только модель чтения; не гарантирует доступность строки к моменту команды |
| Взять следующую проверку | Scope, idempotency key → назначение/пусто/занят | Повтор потерянного ответа возвращает своё исходное назначение; новый запрос занятого жюри не берёт ещё одно |
| Прочитать материал | checkId/solutionId → защищённый материал | Контроль роли, scope и назначения |
| Получить своё текущее назначение | Проверенный субъект → текущие Check, Assignment и версия либо отсутствие назначения | Возврат к той же работе после reconnect; не создаёт назначения и не доверяет старому состоянию браузера |
| Завершить | checkId, outcome, expectedVersion, assignment token, idempotency key | Конфликт после переназначения или при другом outcome |
| Отказаться | checkId, expectedVersion, token, idempotency key | Атомарная передача старшему |

API загрузки/приёма/ручной идентификации решения не входит в Checking (D24). Тестовая инициализация — внутренний bootstrap, не пользовательский endpoint. Предлагаемая HTTP-семантика для проверок: запрет доступа отдельно от конфликта; версия — 409 либо 412 при If-Match, унифицировать перед OpenAPI. Конфликт не маскируется успехом.

## 7. Проверяемые критерии приёмки

| ID | Дано / действие | Ожидаемый результат |
| --- | --- | --- |
| CH-A01 | Два жюри одновременно берут единственный Check | Только одно назначение; второй не получает права завершить тот же Check |
| CH-A02 | Ответ на взятие потерян; тот же запрос повторён | Тот же checkId/token, не новая работа |
| CH-A03 | Назначенный проверяющий завершает корректной версией | Один Completed и один логический вердикт для Results |
| CH-A04 | Вердикт и отказ выполняются одновременно | Один переход, второй — конфликт; нет Completed и новой очереди одновременно |
| CH-A05 | Проверяющий отказался | Его token недействителен, запись только в очереди старшего |
| CH-A06 | Не-владелец или команда завершает Check | Отказ в доступе, состояние/события не меняются |
| CH-A07 | Повтор завершения с тем же key/телом | Исходный результат без второй оценки; с другим телом — конфликт |
| CH-A08 | Брокер недоступен после завершения | Вердикт и outbox сохранены, после восстановления Results получает факт |
| CH-A09 | Один запрос перепроверки доставлен дважды/с новым messageId | Один Check на appealId, подтверждение с тем же checkId |
| CH-A10 | Перепроверка подтверждает прежний вердикт | Всё равно публикуется завершение для подтверждения Results |
| CH-A11 | Подготовлен принятый снимок и доступный материал | Жюри читает исходный материал без загрузки/QR/выбора задачи в текущем приложении |
| CH-A12 | Материал по подготовленной ссылке недоступен | Ошибка чтения наблюдаема; она не становится Incorrect/0, факт загрузки не имитируется |
| CH-A13 | Источник/тестовый bootstrap повторил снимок или прислал другой solutionId на тот же ключ | Идентичный повтор не создаёт Check, несовместимый вход не перезаписывает снимок/материал |
| CH-A14 | Один уже принятый вход обрабатывается конкурентно | Один SolutionReference и один первичный Check; это не конкурентная загрузка от команды |
| CH-A15 | Один жюри одновременно берёт две разные работы разными запросами | Только одно активное назначение, второй новый захват отклоняется как занятость |
| CH-A16 | У жюри есть незавершённая работа, он открывает другую очередь/вкладку | Второе назначение не выдаётся; лимит не считается отдельно по очередям |
| CH-A17 | Жюри завершил работу, Results ещё не обработал событие | При отсутствии иной занятости можно взять следующую проверку |
| CH-A18 | После обычного отказа старший занят | Работа ожидает в SeniorQueued, не получает отрицательный вердикт и не занимает старшего вторым активным назначением |
| CH-A19 | Старший завершает переданную работу | Один финальный вердикт по этой проверке и освобождение занятости старшего |
| CH-A20 | Доступна задача, отличная от ранее проверенной этим жюри | Назначение не ограничивается номером/типом задачи при наличии права на турнир и отсутствии занятости |
| CH-A21 | Обычный проверяющий передал отказную работу старшему, тот занят | Обычный жюри свободен и может взять следующую; прежняя работа остаётся SeniorQueued |
| CH-A22 | Проверяющий закрыл страницу/потерял связь и вернулся | То же назначение и материал восстановлены с backend; новой проверки и автоматического отказа нет |
| CH-A23 | Назначение есть, клиент долго отсутствует | Занятость сохраняется; одно отсутствие связи/истечение времени не освобождает работу |
| CH-A24 | API перезапущен при сохранной БД | Текущее назначение/занятость восстановимы из БД без создания новой проверки |
| CH-A25 | Завершение/отказ сохранены, ответ потерян, клиент вернулся | Показано актуальное состояние; Completed не открывается, SeniorQueued не возвращается обычному жюри |
| CH-A26 | Запрос перепроверки содержит конкретного выбравшего reviewerId | При свободном жюри создан один Appeal Check, сразу Assigned именно ему; другой исполнитель не подставляется |
| CH-A27 | Выбравший жюри конкурентно получает обычную работу | Одно активное назначение; при ReviewerBusy апелляционный Check не создаётся |
| CH-A28 | BaseCheck имеет источник SeniorEscalation | Перепроверка по новой апелляции не создаётся, запрет D14 не обходится служебным запросом |
| CH-A29 | Старший завершает обычную переданную работу | CheckCompleted содержит SeniorEscalation; роль человека сама по себе не подменяет происхождение |
| CH-A30 | После ReviewerBusy поступила новая подтверждённая попытка выбора того же Appeal | При свободном новом выбравшем возможно одно назначение; успешный Check остаётся уникальным на appealId |
| CH-A31 | RequestedReviewerId равен автору baseCheck | Это не препятствует назначению при свободном жюри и корректных связях |
| CH-A32 | Вовремя поданный Appeal выбран/доставлен в Checking после ручного конца | При свободном жюри назначается; завершение публикует CheckCompleted без отказа по текущей неактивности турнира |
| CH-A33 | Назначенный апелляционный жюри отказался | Тот же Appeal Check в SeniorQueued; старый token снят, жюри свободен, RecheckEscalated сохранён |
| CH-A34 | Старший завершил переданную апелляционную проверку | Тот же checkId/appealId, новый assignmentId; kind=Appeal, decisionOrigin=SeniorEscalation, фактический reviewerId старшего и цепочка передачи |
| CH-A35 | Принятое до конца первичное решение ещё Queued | Его можно взять/завершить после конца с обычным лимитом |
| CH-A36 | Любой вердикт отправлен без комментария | Бинарный исход принимается; поля комментария в форме/команде MVP нет |
| CH-A37 | Отказ апелляционного жюри состязается с завершением | Либо Completed, либо SeniorQueued; два перехода одновременно невозможны |

Для CH-A01/A04/A14/A15/A27/A37 нужны реальные конкурентные транзакции PostgreSQL. Отказ апелляционного жюри, первоначальный исполнитель, оба вида проверок после конца и отсутствие комментария заданы. Ручное освобождение зависших назначений ещё открыто. Исполняемые domain/API/PostgreSQL/broker тесты и браузерные V1–V6 реализованы; результаты — в [сводке](../../implementation/progress.md).
