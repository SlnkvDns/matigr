# 003 — Апелляции и перепроверка

Статус: **одобрена пользователем 23 октября 2026 года** вместе со спецификациями 001 и 002. Основа для следующего этапа планирования; код приложения этим одобрением не поручен. Явно открытые вопросы и технические варианты сохраняют свой статус. Основания: [диаграмма](../../event-storming/tournament.mmd), [архитектура и Qxx](../../architecture/architecture.md), [контракты](../../architecture/event-contracts.md). Зависимости: [Checking](../001-checking/spec.md), [Results](../002-results/spec.md).

## 1. Назначение и границы

Команда оспаривает опубликованный результат в пределах регламента. Принятая апелляция приводит к перепроверке того же материала. Новый вердикт подтверждает или меняет результат; команда видит состояние процесса и согласованный итог.

Основа диаграммы: A9 и A7; C22–C27; E23–E28; P8–P10; RM7/RM8; E27 → C21 Results. Appeals владеет допустимостью и ходом процесса. Проверяет решение Checking, начисляет/публикует результат Results. Appeals не меняет их БД и не хранит собственный авторитетный score.

Отклонение, отзыв, дополнительные раунды, новый материал и жалобы вне результата диаграммой не заданы. Их нельзя добавлять как требования. Очередь апелляций не является очередью проверок: первая живёт в Appeals, исполнитель второй — в Checking.

Уточнение пользователя от 23 октября 2026 года (D01): повторная отправка решения задачи запрещена; апелляция относится к единственному принятому материалу. D02 задаёт одну незавершённую проверку на проверяющего, D12 — личную перепроверку выбравшим апелляцию жюри. D03/D14 определяют финальный вердикт старшего после обычного отказа и запрет его обжалования.

Дополнительно согласовано D06–D09: Results автоматически публикует первичные результаты и изменения после апелляций; итог — сумма баллов задач, равные суммы дают общее место с нумерацией 1, 1, 2; общая таблица с баллами по задачам доступна без входа. Подать апелляцию по-прежнему может только уполномоченная команда: публичное чтение таблицы не даёт права на команды изменения.

### Уточнения, согласованные пользователем 23 октября 2026 года

- D10 / часть Q02: после публикации апелляцию можно подать до конца турнира без отдельного лимита минут. D16 уточняет: конец наступает по действию организатора, не по расписанию. Изменение результата не открывает новый срок/квоту; точная серверная точка допуска пограничного запроса ещё Q02.
- D11 / часть Q07: апелляция рассматривается вручную членом жюри, когда он видит поданную апелляцию и выбирает её для проверки. Подача не означает автоматического начала перепроверки. Для этого зарегистрированная апелляция должна быть видна жюри до начала рассмотрения.
- D12 / часть Q05: начальное назначение получает выбравший апелляцию жюри; общий лимит сохраняется. При его отказе действует подтверждённое исключение D18 — передача старшему.
- D13 / Q08: допускается одна апелляция команды на задачу турнира. Это ограничение за весь процесс, не только одна активная и не одна на версию результата. После закрытия/изменения результата новая подача запрещена.
- D14 / Q08: вердикт старшего жюри, вынесенный после отказа обычного проверяющего, нельзя обжаловать. Backend проверяет происхождение вердикта по доверенному основанию Results, а не по полям формы или скрытой кнопке.
- D15 / часть Q05: первоначальный проверяющий может выбрать апелляцию и перепроверить своё исходное решение. Дополнительного запрета по равенству reviewerId нет.
- D16 / часть Q02/Q14: организатор сам завершает турнир; расписание/автоматический таймер не заменяют этот факт.
- D17 / часть Q14: поданную до конца апелляцию можно взять и завершить после конца турнира. Очередь/назначения сохраняются, итог автоматически публикуется и может обновить таблицу.
- D18 / часть Q05: жюри может отказаться от уже взятой апелляции; тот же Check передаётся в очередь старшего, отказавшийся свободен. Старший завершает ту же апелляцию, новая не создаётся.
- D19 / часть Q14: первичные решения, принятые до конца, тоже можно брать/завершать после конца. D20 / Q04: комментарии жюри к любому вердикту, включая апелляционный, не нужны.

Основные маршруты подтверждены D12–D20, включая отказ апелляционного жюри/старшего как фактического завершившего и оба вида проверок после конца. Открыты техническая граница подачи и тестовый ввод конца, материал/тестовый вход и дополнительные функции отклонения/отзыва вне основного процесса. Полный турнирный контекст остаётся вне MVP.

## 2. Подтверждённые правила и предложения

**Подтверждено:** апелляция доступна только после публикации результата (P8), подаётся в установленный срок (P9), после принятия создаётся перепроверка (P10). Перепроверка подтверждает прежний либо изменяет результат (E26/E27); затем апелляция закрывается (E28).

**Не определено:** точная транзакционная граница подачи при ручном конце, отдельное отклонение до перепроверки/отзыв командой и восстановление аномалии. Отказ от уже взятой проверки определён D18 и не равен отклонению апелляции. Комментарии к вердикту исключены D20; текст самой подачи командой — отдельный вопрос Q07.

**Предлагается технически:** проверять допустимость до успешной регистрации, хранить исходное время/основание, обеспечивать постоянную уникальность tournamentId/teamId/taskId, адресовать запрос Checking выбранному жюри и закрывать после подтверждения Results. Квота D13 и запрет D14 уже согласованы; механизм назначения/надёжности остаётся архитектурным предложением.

## 3. Участники и права

Команда подаёт единственную апелляцию до ручного конца, если нет D14, и читает статус. Свободный жюри выбирает/начинает лично, включая первоначального автора; при отказе тот же Check завершает старший (D18). Выбор/передача/завершение разрешены после конца для уже зарегистрированного. Checking контролирует занятость/историю назначений, Appeals — процесс. Организатор задаёт факт конца; в MVP только тестовый адаптер ввода.

Results предоставляет доверенное основание. Checking принимает служебный запрос на новую проверку и сообщает её состояние. Все служебные отправители аутентифицируются; teamId/resultVersion из клиентской формы проверяются по серверному результату.

## 4. Агрегат и процесс

Предлагаемые поля Appeal: appealId, постоянный ключ tournamentId/teamId/taskId, основание resultId/version/solution/material/baseCheck/decisionOrigin/publicationId, время/основание допуска, selectedReviewerId/время выбора, requestId попытки/checkId, currentAssignmentId/currentReviewerId (если известны), escalationId/версия состояния Check, receipt и история. SelectedReviewerId отражает исходный выбор и берётся из проверенного субъекта. При начальном назначении reviewerId ему равен; после подтверждённой передачи D18 фактический исполнитель — старший. История попыток/назначений сохраняется, а прежний выбранный не подменяется задним числом.

Комментариев жюри к исходу нет (D20). Текст/обоснование самой подачи командой, отдельный отзыв и их видимость ещё не определены Q07/Q16; это не комментарий проверяющего, обязательное поле не добавляется. D13 допускает одну апелляцию по задаче; технические повторы, попытки назначения и передача старшему остаются внутри неё.

### Предлагаемая схема состояний

| Состояние | Смысл и выход |
| --- | --- |
| Registered | Апелляция подана допустимым образом, видна жюри и ожидает ручного выбора для рассмотрения (D11) |
| AcceptedAwaitingRecheck | Выбор конкретного жюри и адресованный запрос сохранены; его занятость/назначение ещё должен подтвердить Checking. Предлагаемое сопоставление C23/E24 |
| RecheckPending | Checking создал и назначил Check именно выбравшему жюри; ожидается его вердикт |
| AwaitingSeniorReview | Checking передал тот же Appeal Check старшему после отказа; ожидается его очередь/назначение/вердикт, исходный выбранный уже свободен |
| AwaitingResultApplication | Вердикт сохранён Checking; Results ещё не подтвердил применение |
| Closed | Results подтвердил обработку нужной оценки и доступность автоматически опубликованного результата |
| NeedsResolution | Запрос неисполняем/результат устарел/другой бизнес-конфликт; успешное закрытие невозможно |

Это автомат процесса, расширяющий неполную диаграмму для надёжной интеграции. После D06 отдельное состояние AwaitingPublication не требуется: применение и публикация коррекции происходят в Results вместе. Статусы UI могут быть проще, но не скрывать ожидание/конфликт. Переходы по событиям проверяют корреляцию, допустимость и версии; поздние промежуточные сообщения не откатывают Closed. Не нужны все промежуточные уведомления для обработки уже достоверного финального подтверждения Results.

## 5. Инварианты

1. Регистрация требует доверенного опубликованного основания и открытой подачи до ручного конца. Клиентский кэш не является основанием. При ручном выборе/завершении уже поданного после конца окно не проверяется заново как запрет назначения (D17).
   По D14 происхождение SeniorEscalation запрещает новую подачу. Это источник конкретного вердикта после передачи, а не просто наличие роли Senior у человека.
2. Привязки команды/задачи/материала/baseCheck и базовая версия сохраняются при регистрации; новый ручной выбор не меняет основание. Перепроверка не меняет материал.
3. Время и основание допуска фиксируются сервером; повтор не создаёт новое время/Appeal. D10/D16 ограничивают новую подачу ручным завершением организатора. Предложение: Appeals сериализует регистрацию и закрытие на служебной записи окна, сохраняя его версию/основание. Источник конца уже известен; конкретный критерий для запроса, пришедшего до конца, но регистрируемого позже, ещё Q02.
4. По D11 одна подача не создаёт запрос перепроверки автоматически. Предложение: ручное начало рассмотрения сопоставить C23/E24 и сохранить вместе с outbox в одной транзакции Appeals; это сопоставление уточняется с исполнителем Q05. Доставка повторяема, создание Check идемпотентно по appealId/recheckRequestId.
5. После завершения Checking Appeals ждёт обработки Results. Даже неизменный вердикт не является достаточным подтверждением актуальности базы.
6. Закрытие требует совпадающих appealId/requestId/checkId/resultId/базы и selectedReviewerId исходного выбора в доверенном receipt. Без передачи фактический reviewerId равен выбранному; после D18 допускается фактический старший при evaluationDecisionOrigin=SeniorEscalation, assignmentId/escalationId подтверждённой цепочки. Receipt содержит эти сведения даже при доставке раньше RecheckEscalated/RecheckAssigned. Changed=false всё равно требует регистрации обработки. Сравнение только actual reviewerId с выбранным ошибочно запретило бы разрешённый исход.
7. Конфликт expectedResultVersion не превращается в автоматическое согласие с новым результатом и не перезаписывает его. Дальнейший шаг — согласованная политика Q15.
8. По D13 в Appeals не более одной зарегистрированной апелляции по tournamentId/teamId/taskId независимо от статуса/resultVersion. Постоянное ограничение в БД защищает конкурентные подачи; частичного ограничения только для активных недостаточно. Closed и коррекция результата не снимают квоту.
9. История решения и конфликтов сохраняется. Закрытие не инициирует повторное начисление и не редактирует завершённый Check.
10. Два выбора одной Registered апелляции допускают один переход по версии. RequestedReviewerId — проверенный выбравший жюри, первое назначение получает он. Другая допустимая ветвь — после его отказа новый Assignment старшего на том же Check (D18); произвольная подмена исполнителя не разрешена.
11. Предложение для гонок: при ReviewerBusy Checking не создаёт Check и не назначает работу; Appeals по подтверждённому отказу возвращает ту же апелляцию к ожиданию выбора. Новая попытка после такого отказа получает новый recheckRequestId, но прежний appealId/квоту; технический повтор прежней попытки получает прежний ответ. Поздний ответ другой попытки не меняет текущее состояние. Успешный Check остаётся уникальным по appealId.
12. Отказ после успешного назначения не является ReviewerBusy: тот же Check переводится SeniorQueued, а не возвращается к свободному выбору обычного жюри. Проверяющий освобождён, requestId/appealId/checkId сохранены, новый Assignment старшего связан escalationId. События назначения/передачи не регрессируют по версии Check; поздние промежуточные не открывают Closed.

## 6. Основные сценарии

### AP-01. Подача и проверка допустимости

Условие: команда аутентифицирована, выбран её опубликованный результат. Appeals сначала возвращает ранее успешный идемпотентный ответ, если он есть; иначе получает из Results основание/decisionOrigin и проверяет принадлежность/версию/D14. Затем в локальной транзакции проверяет окно подачи и постоянную уникальность D13, сохраняет регистрацию/основание допуска. Предложение: закрытие и регистрация используют одну блокировку окна; HTTP к Results выполняется до неё. Ручной конец D16 закрывает новые регистрации, но повтор уже успешной подачи возвращает прежний Appeal и после конца. Пограничный критерий Q02 остаётся явно предлагаемым, не согласованным бизнес-правилом.

До публикации успешного принятия нет. При просрочке ответ указывает недопустимость, а не создаёт Check. Сохраняется ли отдельная отклонённая регистрация для аудита — Q07. При недоступности Results API не обещает принятие на основании клиентских данных; предлагается повторяемая техническая ошибка с тем же idempotency key, либо отдельный durable intent после явного согласования. Успешно зафиксированная операция при потерянном ответе возвращается повтором из журнала идемпотентности.

После успешной подачи сохраняется Registered, видимый жюри. E23 обновляет RM7 до ручного начала — уточнение исходной связи E24 → RM7. До выбора нет RecheckRequested/автоматического Check. Выбравший сам перепроверяет, включая первоначального жюри. По D17 очередь остаётся доступной и после конца; ручное начало/завершение не становятся просроченными из-за ожидания жюри.

### AP-02. Создание перепроверки

После ручного выбора Appeals сохраняет его субъект/ID попытки и outbox RecheckRequested с requestedReviewerId. При недоступности брокера UI показывает AcceptedAwaitingRecheck, не обещает назначение. Checking атомарно проверяет занятость жюри, создаёт отдельный Check и сразу назначает именно ему; RecheckAssigned подтверждает персональное назначение. Материал/права читаются через API Checking, token назначения не рассылается брокером.

RequestedReviewerId может совпасть с автором baseCheck (D15). По D17 запрос, его повтор, назначение и завершение допустимы после конца для ранее зарегистрированного Appeal. Сравнение acceptedAt или текущего времени с концом как основание отказа нарушило бы правило; своевременный допуск подтверждает Appeals.

Если при гонке жюри уже занят другой работой, Checking отвечает RecheckRequestRejected(ReviewerBusy), не создавая Check. Предложение: Appeals возвращает ту же зарегистрированную апелляцию к ожиданию ручного выбора; после подтверждённого отказа возможна новая попытка с новым requestId. Это не новая апелляция и не обход квоты. Повтор успешной попытки возвращает то же назначение; успешная перепроверка на appealId одна. Произвольный новый requestId до ответа/для обхода иных конфликтов запрещён.

Невалидные связи материала/базы дают `RecheckRequestRejected` и NeedsResolution. Отказ транспорта не является бизнес-отклонением апелляции. После перезапуска Alerts/операционные данные должны позволять найти зависший процесс; конкретные таймауты не установлены.

### AP-03. Прежний результат подтверждён

Checking завершает новую проверку с прежним outcome. Appeals может показать «перепроверка завершена, ожидается подтверждение результата», но не закрывает её только по E26. Results проверяет актуальность версии, сохраняет receipt и отправляет `ResultEvaluationApplied(changed=false)`.

Если основание актуально и опубликованный результат доступен, Appeals закрывает процесс с итогом подтверждения. Баллы и номер опубликованной версии могут остаться прежними. Если между принятием и применением основание изменилось, no-op не считается безопасным автоматически — нужен конфликт Q15.

### AP-04. Результат изменён

Checking завершает перепроверку с новым outcome; Results условно применяет его к базовой версии, рассчитывает score, делает новую версию и автоматически публикует её с доступным снимком (D06). Подтверждение связывает новую опубликованную версию с конкретной апелляцией и Check. Appeals закрывается после подтверждения Results. Команда перечитывает результат и таблицу в Results; сумма и места учитывают заменённый вклад задачи (D07).

Отдельного ручного утверждения публикации/дополнительного события ожидания нет. Пока Results не обработал вердикт, процесс остаётся AwaitingResultApplication. Само событие E27 от Checking не отправляет напрямую новые баллы в UI.

### AP-05. Устаревшее основание и сбои

Results обнаруживает новую текущую версию и отвечает `ResultEvaluationRejected`. Appeals фиксирует NeedsResolution и сохраняет основание/полученный вердикт. Не создаёт автоматически повторную апелляцию, не меняет expectedResultVersion и не считает прежнюю оценку актуальной. Выбор повторного рассмотрения/отказа/ручного решения — Q15.

Если подтверждение Results пришло раньше RecheckAssigned/CheckCompleted, доверенные ссылки сопоставляются с принятой апелляцией; процесс может завершиться без регрессии при поздней доставке. Если ссылки несовместимы, сообщение изолируется как ошибка, а не закрывает чужую апелляцию. Временные ошибки повторяются; результаты ручного redrive аудируются.

### AP-06. Отказ апелляционного жюри и старший

Назначенный жюри отказывается через Checking. В одной транзакции его token/занятость снимаются, тот же Check переходит SeniorQueued, сохраняются escalationId и outbox RecheckEscalated. Appeals показывает AwaitingSeniorReview. Старший при возможности берёт ту же работу: RecheckAssigned теперь описывает новое назначение с маршрутом SeniorEscalation. Старший завершает без комментария с kind=Appeal; CheckCompleted/receipt Results содержат исходного selectedReviewerId, фактического старшего, assignmentId/escalationId. Ни новую апелляцию, ни дополнительный Check это не создаёт; после конца работает так же. Результат подтверждается/изменяется обычным процессом Results, затем Appeal закрывается.

## 7. Предлагаемая поверхность API и UI

| Возможность | Данные и ограничения |
| --- | --- |
| Подать апелляцию | resultId/ожидаемая версия и idempotency key; автор и команда из проверенного удостоверения; публикация/срок из Results/регламента |
| Прочитать статус | appealId, этап ожидания/итог/доступная причина проблемы, ссылки на базовую и итоговую версии; только разрешённым субъектам |
| Прочитать очередь RM7 | Разрешённый scope жюри, статусы и связи с Check; без создания второй очереди исполнения в Appeals |
| Вручную взять апелляцию | Член жюри, appealId/expectedVersion/idempotency key; selectedReviewerId из удостоверения. Один переход и запрос на персональное назначение; UI ждёт подтверждения Checking |

Команды «подтвердить/изменить результат» из C25/C26 исполняются как завершение Check в Checking, а не как PATCH score в Appeals. Закрытие C27 предлагается автоматическим следствием подтверждения Results, а не кнопкой обхода ожидания; иной регламент требует явного решения.

Frontend показывает этапы ожидания/проверки/обновления/закрытия и наблюдаемый конфликт. После ручного конца новая подача закрыта, но ранее поданное продолжает отображаться и обрабатываться. Скрытая кнопка не заменяет серверную проверку окна. Нет отсчёта минут от публикации или расписанного таймера конца: D16 требует действия организатора. Закрытая подача не означает «все результаты окончательны»; таблица может обновляться от дорассмотрения.

## 8. Проверяемые критерии приёмки

| ID | Дано / действие | Ожидаемый результат |
| --- | --- | --- |
| AP-A01 | Команда оспаривает неопубликованный результат | Нет успешного принятия/перепроверки; ответ соответствует согласованной политике регистрации |
| AP-A02 | Результат опубликован; подача до/после подтверждённого ручного конца | До конца можно подать без интервала от публикации; после новая подача не принимается. Критерий пограничного запроса ещё Q02 |
| AP-A03 | Команда указывает чужой результат | Отказ в доступе без создания процесса |
| AP-A04 | Два одинаковых запроса, первый ответ потерян | Одна апелляция, первоначальное время подачи, одна логическая перепроверка |
| AP-A05 | Один idempotency key повторён с другой базой | Конфликт, существующая апелляция не перепривязывается |
| AP-A06 | Две разные подачи команды по задаче одновременно | Один Appeal по постоянному ключу tournamentId/teamId/taskId; вторая бизнес-подача отклонена, технический повтор идемпотентен |
| AP-A07 | Принятие сохранено, брокер/Checking недоступен | Процесс виден как ожидающий; после восстановления создаётся один Check |
| AP-A08 | Checking подтвердил прежний outcome | До ResultEvaluationApplied апелляция не закрыта; после валидного подтверждения закрыта без повторного начисления |
| AP-A09 | Checking изменил outcome | Закрытие только после применения/публикации Results; итоговая версия прослеживается до апелляции |
| AP-A10 | Базовый результат изменился до применения | Нет перезаписи новой версии; NeedsResolution с причиной |
| AP-A11 | Подтверждение Results доставлено раньше промежуточных событий | Корреляция проверена; поздние события не откатывают финальное состояние |
| AP-A12 | Дубли завершения/подтверждения/закрытия | Одно логическое закрытие, нет второй коррекции или открытия заново |
| AP-A13 | Событие содержит чужой checkId/resultId/requestId | Не закрывает апелляцию, ошибка наблюдаема |
| AP-A14 | Сервис упал после локального коммита до ack брокеру | Повторная доставка безопасна, состояние процесса восстанавливается из БД |
| AP-A15 | При подаче Results недоступен | Нет подтверждённой допустимости из данных клиента; технический исход допускает согласованный повтор |
| AP-A16 | Коррекция успешно применена Results | Она опубликована автоматически, ResultEvaluationApplied указывает доступный снимок; отдельное ожидание ручной публикации не появляется |
| AP-A17 | Команда подала допустимую апелляцию, жюри ещё не выбрал её | Registered виден в очереди жюри; автоматического RecheckRequested по подаче нет |
| AP-A18 | Свободный член жюри вручную выбирает апелляцию | Фиксируется субъект/попытка, Checking назначает её этому же жюри; другой исполнитель не подставляется |
| AP-A19 | Два жюри выбирают одну апелляцию одновременно | Один выбор/успешный Check; проигравший не получает права завершить чужую проверку |
| AP-A20 | Апелляция закрыта с подтверждением или изменением результата | Новая бизнес-подача по той же задаче запрещена независимо от новой версии и оставшегося времени |
| AP-A21 | Результат вынесен старшим после обычного отказа | Подача запрещена по достоверному decisionOrigin; Appeal и Check не создаются |
| AP-A22 | Жюри выбрал апелляцию и конкурентно взял обычную работу | Checking допускает одно активное назначение; при ReviewerBusy апелляция остаётся той же и снова доступна для выбора после ответа |
| AP-A23 | Успешная попытка назначения доставлена повторно | То же назначение тому же жюри, не вторая перепроверка |
| AP-A24 | После подтверждённого ReviewerBusy сделан новый ручной выбор | Новая попытка того же Appeal может назначить свободного выбравшего жюри; квота остаётся занятой прежней апелляцией |
| AP-A25 | Пришла старая ошибка/подтверждение другой попытки | Проверка requestId/корреляции не позволяет отменить актуальное назначение или открыть Closed |
| AP-A26 | Первоначальный проверяющий свободен и выбрал апелляцию | Она может назначаться ему; равенство с автором baseCheck не является запретом |
| AP-A27 | Организатор завершил турнир через тестовый ввод факта | Окно новой подачи закрыто; само прохождение времени без действия его не закрывает |
| AP-A28 | Registered подан вовремя, турнир уже завершён | Свободный жюри может выбрать и начать перепроверку |
| AP-A29 | Назначенная перепроверка завершена после конца | Results применяет/публикует итог, таблица обновляется, Appeal закрывается после подтверждения |
| AP-A30 | После закрытия окна повторён уже успешный запрос подачи | Возвращается тот же Appeal; новый процесс/срок/квота не создаются |
| AP-A31 | После конца получен ReviewerBusy по вовремя поданному Appeal | Та же апелляция вновь доступна для ручного выбора; закрытие новой подачи не запрещает повтор назначения |
| AP-A32 | Выбравший жюри отказался после назначения | Тот же Check передан SeniorQueued, жюри свободен; Appeal не закрыт/не отклонён и не возвращён в обычную очередь |
| AP-A33 | Старший завершил переданную апелляцию | Проверена цепочка selectedReviewerId/assignmentId/escalationId, принят фактический reviewerId старшего; применяется один итог той же апелляции |
| AP-A34 | Receipt старшего пришёл раньше событий передачи/его назначения | Достоверная цепочка в receipt позволяет завершение; поздние события не откатывают Closed |
| AP-A35 | Выбранному жюри пришёл поздний ответ старого назначения после передачи | Он не получает повторно права завершить Check; актуальное состояние берётся из Checking |
| AP-A36 | Старший подтвердил или изменил результат без комментария | Итог принят; поле комментария не требуется ни для вердикта, ни для закрытия |

Для AP-A02 осталась точная серверная граница Q02. Основной процесс, передача старшему, работа после конца и отсутствие комментариев заданы D15–D20. Дополнительные отклонение/отзыв и текст подачи команды ещё не определены. Протокол окна/назначений/событий остаётся техническим предложением; исполняемые тесты пока не создаются.
