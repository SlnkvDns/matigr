# Черновик контрактов сообщений

Актуализация реализации 23 октября 2026 года: CHK-INT-01, RES-INT-01 и APL-INT-01 опубликовали producer/consumer schemas выбранных сообщений и contract tests в [каталоге контрактов](../../contracts/README.md). Эти задачи проверяют форму, fixtures и статические маршруты; runtime producers/consumers, обработчики и интеграционные транзакции ещё не реализованы. Текст ниже сохраняет семантические основания и явно отмечает технические предложения/открытые категории.

Сопоставление producer/consumer, внутренний REST-стык и уточнения имён при планировании: [implementation-contracts.md](implementation-contracts.md). Семантика payload ниже остаётся основой схем сообщений; новые технические предложения требуют ревью планов.

Статус: **семантический проект и основа для отдельных v1 контрактов**, 23 октября 2026 года. Канонические JSON Schemas публикуются отдельно в `contracts/` и проверяются без runtime; это не превращает все предложения документа в утверждённые бизнес-факты и не является готовой конфигурацией брокера. Основания: [диаграмма](../event-storming/tournament.mmd), [архитектура](architecture.md), [карта контекстов](context-map.md).

## 1. Принципы

Доменное событие описывает факт внутри контекста; интеграционный контракт публикуется после локального коммита и содержит только необходимую внешнему потребителю информацию. Не каждое E диаграммы должно стать сообщением брокера. `RecheckRequested` — адресованный асинхронный запрос (команда), несмотря на название в прошедшем времени; его нельзя трактовать как факт создания проверки.

Предлагаемая доставка — at-least-once. Глобальный порядок и exactly-once не предполагаются. Согласованность достигается локальными транзакциями, outbox/inbox, бизнес-ключами и проверкой ожидаемых версий. Брокер/клиент/численные параметры — Q13 в [реестре](architecture.md#12-реестр-открытых-вопросов).

## 2. Общий envelope

| Поле | Смысл |
| --- | --- |
| messageId | Глобально уникальный ID сообщения (event ID для событий); при техническом повторе сохраняется |
| messageType | Идентификатор контракта, например `matigr.checking.check-completed` |
| schemaVersion | Версия схемы payload; не версия бизнес-агрегата |
| producer | Сервис-владелец, проверяется транспортом/учётными данными; строка в JSON сама по себе не доказывает отправителя |
| occurredAt | Время факта в UTC; не используется для разрешения конфликтов и упорядочивания |
| aggregateType, aggregateId, aggregateVersion | Поток производителя и его монотонная версия; сравнивать только внутри одного типа/ID/производителя |
| correlationId | Сквозной ID первичного процесса или апелляции |
| causationId | ID сообщения/команды, вызвавшей этот факт |
| payload | Данные контракта ниже |

Идентификаторы непрозрачны; формат выбирается при схемах. Передаются контрактные данные, не ORM-объекты. D20 исключает комментарии жюри к вердикту; текст решения и бинарный материал в брокер не помещаются. Технические reasonCode, авторство и история передачи остаются для надёжности/аудита, их клиентская видимость — Q16.

Различать: `aggregateVersion` Check меняется при назначении/отказе/завершении; `reviewRevision` относится к цепочке проверок одного solutionId; `resultVersion` — к TeamTaskResult; `schemaVersion` — к структуре сообщения. Ни одна из этих версий не заменяет другую.

## 3. Каталог интеграционных сообщений MVP

| Контракт | Владелец → потребитель | Триггер/диаграмма | Гарантия факта |
| --- | --- | --- | --- |
| `CheckCompleted` | Checking → Results; Appeals для kind=Appeal | Первичный вердикт E17/E18; результат перепроверки E26/E27 | Вердикт сохранён в Checking; начисление ещё не подтверждено |
| `RecheckRequested` | Appeals → Checking | После ручного начала рассмотрения жюри D11; предлагается сопоставить E24/P10/C24 | Запрос сохранён и должен получить ответ; одна подача E23 этого запроса не создаёт; Check ещё может не существовать |
| `RecheckAssigned` | Checking → Appeals | Начальное назначение D12 либо новое назначение старшего D18, E25/E16 | Подтверждён актуальный Assignment на том же Check; тип маршрута отличает выбранного и старшего, общий лимит соблюдён |
| `RecheckEscalated` | Checking → Appeals | Отказ от взятой апелляционной проверки D18, E19/E20 | Тот же Check в SeniorQueued, прежнее назначение/занятость сняты; нового исполнителя ещё может не быть |
| `RecheckRequestRejected` | Checking → Appeals | Добавленный технический/доменный отрицательный ответ, в диаграмме отсутствует | Запрос не может быть исполнен в указанном виде; отказ не означает отказ команды от проверки |
| `ResultEvaluationApplied` | Results → Appeals для kind=Appeal | Подтверждение C20/C21, отсутствует как отдельное E в диаграмме | Вердикт обработан, итоговый снимок доступен по API Results; требуется и при неизменном результате |
| `ResultEvaluationRejected` | Results → Appeals для kind=Appeal; мониторинг для Initial | Добавленная развилка согласованности | Вердикт сохранён как конфликтный/неприменимый, действующий результат им не заменён |

E21/E22 предлагаются как локальные `ResultRecorded`/`ResultChanged`, на их основе Results обновляет свои проекции и сообщает клиентам. В MVP не требуется вторая пара обязательных брокерных сообщений с теми же баллами. Если появятся внешние потребители результатов, отдельный контракт публикации согласуется дополнительно.

E13 (SolutionAccepted) относится к внешнему приёму вне D24, не внутреннему intake-модулю Checking. В локальном MVP стартовые уже принятые решения готовит test bootstrap; producer/загрузка/QR не реализуются. E16/E19/E20 — локальные Checking, для kind=Appeal добавляются RecheckEscalated/RecheckAssigned старшего. E23/E24/E28 — локальные Appeals; RecheckRequested сохраняется с выбором E24, AppealClosed не инициирует вторую коррекцию.

### Граница уже принятого решения — будущий вход, не сервис приёма MVP

Предложение будущего Published Language SolutionAccepted/E13: solutionId, tournamentId/teamId/taskId, materialVersionId, стабильный materialRef, acceptedAt и версия/ID источника. Producer — внешний контекст приёма, который сейчас не создаётся; его QR payload, upload API, файловые лимиты/валидация не входят в эту схему. MaterialRef — защищённый идентификатор/ссылка для чтения, не файл и не истекающая подписанная URL.

Checking переводит снимок в локальный SolutionReference и атомарно создаёт первичный Check. Идентичный вход/инициализация не создаёт дубль, несовместимый solutionId/materialVersionId для занятого ключа — наблюдаемая ошибка. Подготовленные fixtures проходят тот же внутренний переход состояния без симуляции фактов «фото загружено»/«QR распознан» и без пользовательского endpoint. Реализация внешнего producer и живого конвейера приёма не является условием тестирования трёх сервисов. Поздняя доставка уже принятого решения не превращается в новую подачу после конца.

## 4. Payload и правила обработки

### 4.1. CheckCompleted

Обязательные поля: `checkId`, `solutionId`, `materialVersionId`, `tournamentId`, `teamId`, `taskId`, `kind` (`Initial` или `Appeal`), `reviewRevision`, `outcome` (`Correct` или `Incorrect`), `decisionOrigin`, фактический `reviewerId`, `assignmentId`, `completedAt`. Комментарий жюри в payload не нужен (D20).

Предлагаемые значения decisionOrigin: OrdinaryReview — обычная первичная оценка (kind=Initial); AppealReview — оценка лично выбравшего апелляцию (kind=Appeal); SeniorEscalation — финальная оценка старшего после отказа при любом kind (D18). Для SeniorEscalation обязателен escalationId. Kind при передаче не меняется. Происхождение не выводится только из роли человека; Results сохраняет его для опубликованной версии и служебного основания, а receipt различает происхождение обработанной оценки и прежней публикации при no-op.

Для `Initial`: `appealId`, `recheckRequestId`, `baseCheckId`, `publicationId` отсутствуют; `expectedResultVersion=0` означает создание результата при его отсутствии. По согласованному D01/Q03 команда отправляет решение задачи однократно. При существующем результате идентичный checkId дедуплицируется, другой первичный Check/solutionId даёт конфликт целостности; выбор «последней/лучшей» отправки не предусмотрен.

Для Appeal обязательны appealId, recheckRequestId, selectedReviewerId исходного выбора, resultId, baseCheckId, publicationId, expectedResultVersion. При AppealReview фактический reviewerId равен selectedReviewerId, при SeniorEscalation он отражает старшего и связан с тем же Check через assignmentId/escalationId. Outcome оценивает тот же материал; баллы/итог команды не передаются проверяющим. Запрет новой апелляции на базовый SeniorEscalation (D14) не запрещает старшему завершить уже существующую апелляцию (D18).

Checking выдаёт монотонный `reviewRevision` в пределах solutionId, но пропуск номера не означает потерянный `CheckCompleted`: назначенная проверка могла ещё не завершиться. Этот номер не разрешает новую отправку с другим solutionId для того же ключа D01 и не разрешает применять вердикт поверх произвольной версии результата. Полученный повтор `checkId` с другим outcome — нарушение контракта, не новая коррекция; завершённый Check не редактируется.

По D02 завершение Checking атомарно освобождает занятость reviewerId вместе с сохранением вердикта/outbox; жюри не ждёт `ResultEvaluationApplied`, чтобы стать свободным. Сам лимит одной незавершённой проверки обеспечивает Checking локально, а не обработчик событий Results. При передаче старшему по D03 итоговый `CheckCompleted(kind=Initial)` отражает его финальный вердикт по тому же Check/материалу; отказ обычного жюри не публикуется как отрицательный outcome.

По D04 занятость обычного жюри также освобождается в транзакции передачи отказной работы в очередь старшего; межсервисного подтверждения для взятия следующей работы не нужно. По D05 разрыв связи/закрытие страницы не создаёт отказа, завершения или нового назначения: при возвращении продолжается сохранённое. Если завершение/отказ успели закоммититься до потери ответа, API возвращает актуальное состояние; технический повтор не переиздаёт новый логический вердикт.

Results проверяет принадлежность ключа, ссылку на базовую проверку/материал, версию результата и версию scoring rule. Изменение значения по апелляции заменяет вклад задачи; не делает `total += newScore`. Идентичность обработанной оценки — `checkId`; одинаковая оценка не начисляется дважды даже с новым messageId.

### 4.2. RecheckRequested

Каноническая producer schema Appeals и consumer expectation Checking опубликованы раздельно: [Appeals producer](../../contracts/events/appeals/recheck-requested.v1.schema.json), [Checking consumer](../../contracts/events/checking/consumers/recheck-requested.v1.schema.json). Поля: `recheckRequestId` (один на попытку персонального назначения), `appealId`, `requestedReviewerId`, `solutionId`, `materialVersionId`, `tournamentId`, `teamId`, `taskId`, `resultId`, `expectedResultVersion`, `publicationId`, `baseCheckId`, `baseOutcome`, `submittedAt`, `acceptedAt`. RequestedReviewerId — проверенный субъект ручного выбора в Appeals, не произвольный ID из клиентской формы.

Основание сохраняется из доверенного снимка Results; клиент не выбирает произвольные baseOutcome и version. По D10 подача разрешена до конца турнира, отдельного лимита от публикации нет; проверка своевременности принадлежит Appeals и не повторяется Checking как собственное правило. После D11 запрос возникает только после ручного выбора поданной апелляции членом жюри. В предлагаемом сопоставлении C23/E24 acceptedAt — время этого человеческого действия, submittedAt — исходное время подачи; их нельзя подменять друг другом.

По D12 инициатор сам перепроверяет: Checking проверяет полномочия сервиса, связи материала/baseCheck, допустимость requestedReviewerId и общую занятость. По D15 он может быть автором baseCheck; совпадение ID не является отказом. SeniorEscalation в базе запрещает новую апелляцию (D14). В одной транзакции создаются Check/персональное назначение, inbox/receipt и outbox; при ReviewerBusy — только receipt отказа/inbox/outbox, без Check. Единственность Appeal по ключу D13 обеспечивает Appeals, один успешный Check на appealId — Checking.

По D16 конец определяется ручным действием организатора. По D17 acceptedAt, доставка RecheckRequested, assignedAt и completedAt могут быть после конца для зарегистрированного вовремя Appeal. Checking не отказывает по текущей неактивности турнира/своим часам и не переоценивает время подачи: границей допуска владеет Appeals. Повтор назначения после подтверждённого ReviewerBusy также возможен после конца. Results применяет/публикует итог после конца обычным образом.

Для MVP предлагается изолированный тестовый ввод факта конца с сериализацией регистрации/закрытия на записи окна Appeals; он не реализует турнирный контекст. В будущем асинхронная доставка E9 от полноценного источника сама по себе не исключит поздний допуск во время лага. Нужен согласованный протокол авторитетного закрытия/регистрации; его нельзя заменить проверкой occurredAt или простым чтением кэша. Подробности и открытая точка допуска пограничного запроса — Q02 и архитектура.

Технический повтор requestId возвращает сохранённый исход этой попытки: прежнее успешное назначение или прежний ReviewerBusy/иной отказ. Занятость не пересчитывается задним числом для уже обработанного запроса. Новый payload с прежним requestId — конфликт. После подтверждённого ReviewerBusy, когда Check не создан, допускается новый ручной выбор с новым requestId в рамках того же Appeal. После успешного назначения новый requestId с другим reviewerId не переназначает работу и не создаёт второй Check. Повтор с тем же согласованным бизнес-основанием возвращает существующий Check; противоречащие связи — конфликт. Другие отказы не обходятся сменой requestId.

### 4.3. RecheckAssigned

Поля: recheckRequestId, appealId, checkId, selectedReviewerId, фактический reviewerId, assignmentId, assignmentKind (Selected / SeniorEscalation), solutionId/materialVersionId, ключ турнира/команды/задачи, resultId/expectedResultVersion/publicationId, reviewRevision, createdAt/assignedAt. Для SeniorEscalation обязателен escalationId. Начальное Selected назначение обязано совпасть с requestedReviewerId; старшему после отказа назначается тот же Check с новым assignmentId.

Контракт подтверждает персональное назначение: начальное выбравшему (D12) либо последующее старшему после отказа (D18). Первое создаёт Check/Assigned, второе переводит существующий SeniorQueued в SeniorAssigned. Занятость/assignment/outbox фиксируются локально атомарно. Пока нет первого подтверждения, Appeals показывает ожидание назначения. В брокере передаётся assignmentId, но token получают только через защищённый API Checking.

Appeals проверяет requestId, основание, selectedReviewerId и допустимый маршрут назначения. Для Selected reviewerId совпадает с выбранным; для SeniorEscalation проверяются escalationId и тот же Check. Версия envelope относится к Check: старое назначение не откатывает более новую передачу/назначение. Повтор исходного RecheckRequested после передачи возвращает прежний логический исход/Check, но не восстанавливает старое назначение; запоздалое подтверждение исходного Assigned остаётся старой версией. Closed не открывается поздними событиями.

### 4.3a. RecheckEscalated

Поля: recheckRequestId, appealId, checkId, selectedReviewerId, releasedReviewerId, releasedAssignmentId, escalationId, ключ турнира/команды/задачи, resultId/expectedResultVersion, escalatedAt. Состояние после факта — SeniorQueued; envelope несёт версию этого Check.

Отказ, снятие token/занятости, очередь старшего и outbox — одна транзакция Checking. Check/Appeal/исходный requestId не меняются, комментарий к отказу не требуется. Старший берёт работу позже, с общим лимитом; RecheckAssigned сообщает новый Assignment. Это не ReviewerBusy: тот не создаёт Check, а здесь существующий передан старшему и не возвращается к обычному ручному выбору. Для первичного Check E19/E20 остаются локальными; интеграция требуется для состояния Appeal.

### 4.4. RecheckRequestRejected

Поля: `recheckRequestId`, `appealId`, `requestedReviewerId`, `solutionId`, `resultId`, `expectedResultVersion`, `reasonCode`, `rejectedAt`. Предлагаемые категории: ReviewerBusy (персональное назначение не состоялось, Check не создан), неизвестный материал, несовпадение связей, запрещённая база SeniorEscalation, противоречивый повтор. Финальный набор кодов/их схема ещё черновые.

Недоступная БД/брокер — техническая ошибка с повтором той же попытки, не бизнес-отказ. Для ReviewerBusy Appeals по совпадающему requestId снимает неподтверждённый выбор и возвращает тот же Appeal в Registered: он не закрыт, квота не освобождена; следующий ручной выбор может начать новую попытку. Это не автоматическое переназначение другому человеку. Остальные бизнес-конфликты идут в NeedsResolution и не обходятся новым requestId. Запоздалый отказ старой попытки не снимает новое подтверждённое назначение.

### 4.5. ResultEvaluationApplied

Каноническая wire-схема опубликована в [ResultEvaluationApplied schema](../../contracts/events/results/result-evaluation-applied.v1.schema.json). Поля: evaluationId (= checkId), kind=Appeal, фактический reviewerId/assignmentId, evaluationDecisionOrigin из CheckCompleted, solutionId/materialVersionId, ключ турнира/команды/задачи, resultId/expectedResultVersion/resultVersion, previousOutcome/outcome/previousScore/score, scoreRuleVersion, changed, appliedAt, publicationId/publicationState. Для апелляции также обязательны appealId, recheckRequestId, baseCheckId, selectedReviewerId и basePublicationId. `basePublicationId` сохраняет исходный publicationId основания CheckCompleted; `publicationId` — итоговая доступная публикация. Для SeniorEscalation обязателен escalationId.

В envelope receipt использует `aggregateType=EvaluationReceipt`, `aggregateId=evaluationId`, `aggregateVersion="1"`: один терминальный receipt на evaluationId, повторы публикуют тот же receipt, не новую версию. Результат initial остаётся локальной записью Results и не маршрутизируется в Appeals.

Для апелляции обязательны appealId, recheckRequestId, baseCheckId и исходный selectedReviewerId. Для Initial поля апелляции отсутствуют, previousOutcome/previousScore могут отсутствовать.

Appeals сопоставляет selectedReviewerId исходному выбору и проверяет маршрут: при AppealReview фактический reviewerId ему равен, при SeniorEscalation допустим старший с assignmentId/escalationId той же цепочки. Данные приходят в доверенном receipt и достаточны даже до доставки RecheckEscalated/назначения старшего. ReviewerId/evaluationDecisionOrigin относятся к обработанной оценке, а не авторству прежней публикации при changed=false; no-op receipt её происхождение не меняет.

По согласованному D06/Q01 Results автоматически публикует результат, включая коррекцию по апелляции. В успешном `ResultEvaluationApplied` publicationId обязателен и относится к доступной итоговой опубликованной версии; publicationState имеет значение Published. Pending/unpublished не являются успешным подтверждением этого контракта в MVP. Ссылка на исходную публикацию апелляции сохраняется отдельно в её основании и не подменяется итоговой.

`changed=false` допустимо: проверка зарегистрирована как обработанная и ссылается на ту же актуальную версию результата; resultVersion и итоговый `publicationId` совпадают с основой, но receipt по evaluationId обязателен. Если outcome изменился при неизменном числовом score, это всё равно изменение бизнес-результата: `changed` относится к авторитетным полям результата, а не только к сумме.

`changed=true` означает новую версию результата и её автоматическую публикацию. Повтор evaluationId возвращает ранее зафиксированное подтверждение без новой версии, повторного начисления или нового publishedAt. При changed=false сохраняется исходная публикация и её время. История обработки с полученным scoreRuleVersion сохраняется. D10 ограничивает подачу концом турнира; D13 запрещает следующую апелляцию после уже зарегистрированной независимо от новой версии или времени. Коррекция и повтор сообщения не обнуляют квоту и не создают новый срок.

Для закрытия апелляции требуется подтверждение доступного опубликованного результата. По D06 оно формируется после фиксации результата и согласованного публичного снимка, отправляется из outbox; отдельного контракта/этапа подтверждения публикации нет. По D08 таблица публична, но служебное сообщение не открывает материал, сведения проверяющего и внутреннее основание апелляции анонимному посетителю. Уведомления браузеру содержат только согласованные публичные поля либо инвалидацию снимка.

### 4.6. ResultEvaluationRejected

Каноническая wire-схема опубликована в [ResultEvaluationRejected schema](../../contracts/events/results/result-evaluation-rejected.v1.schema.json). Поля: evaluationId, kind=Appeal, фактический reviewerId/assignmentId/evaluationDecisionOrigin, ключ турнира/команды/задачи, solutionId, resultId (если существует), expectedResultVersion/actualResultVersion (если существует), reasonCode/rejectedAt, appealId/recheckRequestId/baseCheckId/selectedReviewerId; для SeniorEscalation — escalationId. Корреляция учитывает разрешённую передачу, не только исходного выбранного. Точный набор reasonCode оставлен открытым до утверждения категорий; схема не закрепляет произвольный enum.

Категории: конфликт базовой версии, неизвестное правило начисления, неверная связь решения/результата, нарушение запрета повторной отправки D01. Отличать невалидный payload, постоянный бизнес-конфликт и временно отсутствующую зависимость. Отсутствие первичного результата из-за перестановки событий сначала требует ожидания/проверки зависимости, а не немедленного окончательного отказа.

При ошибке версии Results не подменяет expectedResultVersion актуальным значением и не повторяет запись поверх него. Appeals остаётся в явно конфликтном состоянии; дальнейшее бизнес-действие зависит от Q15. Для обычной первичной проверки конфликт также виден в журнале/операционном представлении, а не теряется без потребителя.

## 6. Пример нормального процесса апелляции

Числа — пример версий, не бизнес-лимиты.

```mermaid
sequenceDiagram
    participant Team as Команда
    participant A as Appeals
    participant R as Results
    participant B as Брокер
    participant C as Checking
    participant J as Проверяющий
    Team->>A: Подать апелляцию на resultId, version=1
    A->>R: Получить опубликованное основание
    R-->>A: publicationId, version=1, publishedAt, rule
    Note over A: Проверка подачи до конца турнира; Registered в очереди
    J->>A: Вручную выбрать апелляцию для личной проверки
    Note over A: Предложение: принятие E24 + outbox
    A->>B: RecheckRequested(expectedResultVersion=1, requestedReviewerId)
    B->>C: RecheckRequested
    Note over C: Свободен ли жюри; Check + назначение + inbox + outbox
    C->>B: RecheckAssigned(checkId, reviewerId)
    B->>A: Перепроверка создана
    J->>C: Завершить своё назначение перепроверки
    C->>B: CheckCompleted(kind=Appeal)
    B->>R: Завершённый вердикт
    B->>A: Завершённый вердикт
    Note over R: Проверка версии; результат/receipt + inbox + outbox
    R->>B: ResultEvaluationApplied(changed=true, version=2)
    B->>A: Подтверждение доступного результата
    Note over A: Проверка связей; закрытие + inbox
    Team->>R: Прочитать актуальный результат/таблицу
```

Если `changed=false`, результат может остаться version=1, но подтверждение всё равно нужно. Ветви доставки в Appeals/Results независимы: подтверждение Results может прийти в Appeals раньше CheckCompleted или RecheckAssigned. Appeals связывает ответы по сохранённым requestId/appealId/ключу результата/базовой версии, принимает терминальное подтверждение от доверенного Results и не регрессирует при поздних промежуточных сообщениях.

Схема показывает маршрут без отказа: выбравший сам завершает, включая первоначального жюри (D12/D15). При D18 та же работа передаётся старшему через RecheckEscalated, новое RecheckAssigned и итог с цепочкой передачи. ReviewerBusy отличается: Check ещё не создан, апелляция возвращается к выбору. D13 запрещает повторную подачу, D14 — новую апелляцию на исходный финальный вердикт старшего. D17/D19 разрешают обработку уже принятого после конца, включая передачу/публикацию; комментариев к вердикту нет.

## 7. Повторы, конкуренция и ошибки

1. **Outbox:** запись бизнес-изменения и исходящего сообщения одной транзакцией PostgreSQL. Отправитель помечает отправленное после подтверждения транспорта; сбой между публикацией и отметкой даёт дубль.
2. **Inbox:** уникальность `(consumer, messageId)`, изменение агрегата, сохранение ответа/outbox и отметка обработки в одной транзакции. Подтверждение брокеру — после коммита. Inbox не должен навечно отмечать обработанным событие, чей бизнес-переход не зафиксирован.
3. **Бизнес-идемпотентность:** локальный SolutionReference входного принятого снимка (D01/D24) и Appeal (D13) уникальны по tournamentId/teamId/taskId; первичный Check на solutionId, перепроверка на appealId, receipt по checkId. Это не реализация приёма A6. Новый requestId после ReviewerBusy не создаёт Appeal. MessageId не заменяет бизнес-ключ; общий лимит reviewerId защищается отдельно.
4. **Версии:** Result применяется через compare-and-swap к expectedResultVersion; создание при version=0 — только при отсутствии строки по ключу. Повтор уже применённого evaluation проверяется раньше CAS, иначе успешный дубль ошибочно станет конфликтом.
5. **Порядок:** состояние нельзя вычислять по последнему occurredAt. Сообщение старой версии не должно откатывать запись; неизвестная зависимость сохраняется для повторной обработки. Для одного результата недостаточно просто сравнить aggregateVersion разных Check.
6. **Ошибки:** временные сбои повторяются с ограниченным backoff; исчерпание попыток ведёт в наблюдаемую очередь ошибок с сохранёнными причинами/корреляцией. Бизнес-конфликт имеет явный ответ. Неизвестная schemaVersion не теряется и не применяется приблизительно. Численные лимиты/retention — Q13.
7. **Восстановление:** повторная отправка сохраняет messageId, requestId и бизнес-основание. Ручной redrive аудируется. Нельзя лечить конфликт обновлением payload старого события; новое бизнес-решение требует нового факта и согласованной команды.

## 8. Версионирование и контрактная проверка

Предложение: аддитивные необязательные поля совместимы, удаление/изменение смысла/типа обязательного поля требует новой schemaVersion и периода совместимости. Новое enum-значение не считать автоматически совместимым со всеми потребителями. Схемами владеют производители, принимающие изменения — известные потребители. В монорепозитории нельзя требовать одновременного развёртывания всех сервисов ради каждой добавки.

При runtime-реализации дополнительно проверить: повтор идентичного сообщения, повтор бизнес-операции с новым messageId, конфликтующий payload, перестановку подтверждений, неизвестную версию, CAS-конфликт и восстановление после падения до/после коммита. Статические формы, примеры и связи consumer/provider уже проверяются contract tests; они не заменяют runtime integration tests.

Q01/Q03/Q04/Q08/Q11/Q12 закрыты для текущего объёма. D22 фиксирует стоимость, D23 — заменяемый тестовый вход, D24 исключает весь приём; SolutionAccepted — описание будущей внешней границы, не новый deployable. Основной поток трёх сервисов задан; технические схемы/протоколы остаются черновыми. Открыты точка допуска ручного конца Q02/Q14, дополнительные scope Q05, отклонение/отзыв/текст подачи Q07, транспорт Q13 и аномалии Q15. Сообщения не являются публичным API браузера.
