## 2. Общие правила HTTP

- Префиксы: `/api/v1/checking`, `/api/v1/results`, `/api/v1/appeals`. Межсервисное чтение — `/internal/v1/results`. Dev-адаптеры — `/dev/v1`, выключены вне local/test. Сервисные credentials и пользовательские удостоверения различаются.
- Изменяющие пользовательские POST требуют `Idempotency-Key`. Область ключа: subjectId + операция + ключ. Сохраняются нормализованный hash запроса и исходный ответ. Повтор успешно исполненной команды проверяется **до** ETag/окна/текущего состояния; другой payload с тем же ключом → `409 IdempotencyConflict`. Проверка личности и принадлежности результата остаётся обязательной.
- GET агрегата возвращает ETag; действия над известным состоянием требуют `If-Match`. Нет заголовка → `428`, устарел → `412`; конфликт бизнес-состояния/занятости → `409`. Взятие следующей работы не требует ETag, поскольку выбирает её сервер. Потерянный ответ восстанавливается повтором с тем же ключом и GET своего состояния.
- `400` — некорректная форма, `401/403` — отсутствие удостоверения/полномочий, `404` — недоступный объект, `503` — временная зависимость. Ответы об ошибках — ProblemDetails с машинным `code` и `correlationId`, без частных материалов/токенов. Ошибки проверки базы при подаче различают конфликт версии и временную недоступность.
- `201` означает зарегистрированную апелляцию; `202` при ручном выборе означает сохранённую попытку, **не подтверждённую занятость**. Checking подтверждает назначение асинхронно. Публичный GET/SSE таблицы не требует входа.
- UI получает полномочия с backend. reviewerId/teamId не задают владельца командой из браузера. Assignment token доступен только актуальному владельцу через защищённое чтение Checking и никогда не передаётся в брокер.

## 3. Синхронный стык Results → Appeals

**Единственный необходимый межсервисный REST-вызов MVP:**

`GET /internal/v1/results/{resultId}/appeal-basis?expectedResultVersion={version}`

Владелец — Results; потребитель — Appeals под сервисным удостоверением. `200` возвращает только опубликованное актуальное основание: resultId, resultVersion, tournamentId/teamId/taskId, solutionId/materialVersionId, sourceCheckId, decisionOrigin, outcome, scoreRuleVersion, publicationId, publishedAt и publicationState=Published. Не возвращает материал, assignment token или право подать апелляцию. Appeals самостоятельно проверяет команду, окно и постоянную квоту. В своём снимке Appeals сохраняет sourceCheckId как baseCheckId.

`409 ResultVersionConflict` — актуальная версия отличается; `404 PublishedResultNotFound` — опубликованного результата нет; `503`/таймаут — не разрешать подачу по кэшу, вернуть временную ошибку без расходования квоты. HTTP выполняется до транзакции регистрации. В обычном MVP до первой апелляции нет легального конкурентного изменения результата той же задачи; аномалию всё равно защищают версии и последующий CAS Results. Чтение по HTTP само по себе не создаёт распределённую транзакцию.

Входной POST Appeals содержит resultId/expectedResultVersion, а не доверенный клиентский снимок. Публичные данные таблицы недостаточны для внутреннего основания; права на апелляцию не вычисляются из роли автора на frontend.

## 4. Матрица сообщений

Поля и условия обязательности определены в [event-contracts.md](event-contracts.md#4-payload-и-правила-обработки); ниже — маршрутизация и ответственность. Направленный `RecheckRequested` — интеграционная команда, остальные — факты/результаты обработки.

| Сообщение | Владелец producer | Consumer и очередь | Идемпотентность и эффект |
| --- | --- | --- | --- |
| RecheckRequested | Appeals | Checking: `checking.recheck-requests.v1` | requestId + hash; один успешный Check на appealId; попытка ReviewerBusy не создаёт Check |
| RecheckAssigned | Checking | Appeals: `appeals.checking-facts.v1` | appealId/requestId/checkId, Check aggregateVersion; Selected либо SeniorEscalation, не откатывать поздними фактами |
| RecheckEscalated | Checking | Appeals: та же очередь фактов | Та же перепроверка/попытка; освободить прежнего жюри, отразить ожидание старшего |
| RecheckRequestRejected | Checking | Appeals: та же очередь фактов | Только текущая попытка; ReviewerBusy → Registered, иной постоянный конфликт → NeedsResolution |
| CheckCompleted | Checking | Results: `results.check-completed.v1`; Appeals: своя очередь фактов только kind=Appeal | Results: evaluationId=checkId до CAS; Appeals: ожидать Results, не закрывать по вердикту |
| ResultEvaluationApplied | Results | Appeals: `appeals.result-receipts.v1` только kind=Appeal; Initial — локальный журнал Results | Закрытие по полному receipt доступного опубликованного результата, включая changed=false |
| ResultEvaluationRejected | Results | Appeals: та же очередь receipts для kind=Appeal; Initial — локальный журнал/диагностика Results | Коррелированный постоянный конфликт; не менять базу и не начислять баллы |

Bindings фильтруют kind маршрутом, но потребитель дополнительно проверяет payload. Копия CheckCompleted для Results и Appeals идёт в **разные** очереди: конкурирующие consumers одной очереди не должны делить этот факт между сервисами. E21/E22/E23/E24/E28 и первичные E19/E20 не требуют дополнительных дублирующих интеграционных сообщений. `SolutionAccepted` — будущий внешний контракт, live consumer/producer и загрузка не входят в MVP; bootstrap использует внутреннюю операцию Checking.

Во всех сервисах inbox по `(consumer, messageId)`, hash payload и бизнес-ключи дополняют друг друга. Повтор того же business ID с новым messageId не повторяет эффект; противоречащий payload — нарушение контракта. В планах/таблицах хранения `requestId` — короткое имя попытки; **в wire payload каноническое поле называется `recheckRequestId`**. Outbox хранит стабильные messageId и envelope. Ack брокеру — после локального commit. Несовместимая schemaVersion/невалидный payload сохраняются в карантине, временная ошибка повторяется с backoff; redrive сохраняет логическую идентичность. Retention и эксплуатационные параметры — Q13, не произвольные бизнес-сроки. До решения retention не вводить автоматическую очистку receipts, нарушающую гарантии повторов; постоянная уникальность Appeal не зависит от их хранения.

| Стык | Согласованное решение в планах | Проверка при реализации |

| Завершение → результат | Checking не присылает баллы; Results использует свои фиксированные правила и expectedResultVersion | CH-A10, RS-A01–10/31 |

| Публичность | GET/SSE таблицы анонимны; материал, основание и команды защищены | RS-A19/21, негативные E2E |

На уровне документов входы/выходы семи сообщений и REST-стык сопоставлены. В CHK-INT-01 опубликованы [Checking OpenAPI и четыре producer JSON Schema](../../contracts/README.md), входная fixture/consumer expectation RecheckRequested и проверки формы/семантических связей. Контракты Results/Appeals и runtime-совместимость всех сторон ещё не созданы/не проверены; CHK-INT-04 и соседние integration-задачи остаются открытыми.

Статическая проверка подготовленных документов: глобальные ID задач уникальны, все зависимости существуют, граф ацикличен; локальные ссылки/якоря и столбцы таблиц корректны. В строках задач прослеживаются все CH-A01–37, RS-A01–31 и AP-A01–36. Первый V1 не зависит от реализации поздних апелляционных сценариев. Эта проверка подтверждает целостность декомпозиции, но не заменяет будущие unit/integration/E2E тесты.

## 6. Общий порядок вертикальных сценариев

Общая веха `MVP-REVIEW` **пройдена 23 октября 2026 года**: пользователь одобрил планы и задачи трёх сервисов. Согласование документации отделено от поручения выполнять реализацию: задачи открыты, код не начат. При таком поручении повторно одобрять те же планы не требуется. Зависимости задач используют глобальные ID из трёх tasks.md; номер сценария задаёт порядок приёмки, а не запрет параллельно готовить независимые части.

| Сценарий | Проверяемый сквозной результат | Задачи приёмки |

| V1 | Подготовленный материал → обычный жюри → вердикт → автоматическая публикация → анонимная таблица | CHK-E2E-01, RES-E2E-01 |

Каждый сервис владеет своим OpenAPI; каждый producer — своей схемой сообщения, consumer проверяет её совместимость.

## 7. Решения и оставшиеся вопросы

- Q02/Q14: T05 и тестовый факт ручного конца в Appeals приняты для локального MVP, без управления турниром. Протокол будущего авторитетного upstream остаётся открытым.

- Q09: отдельный pending status и пустая сумма=0 приняты с планом Results, без приравнивания к Incorrect. При реализации 23 октября пользователь явно согласовал тестовые задачи 10/20 целых баллов и строки JSON для баллов/версий. Профиль v1 и T07 закреплены в [runtime-baseline.md](runtime-baseline.md); будущая шкала вне этого профиля не задана.
- Q10/Q13: T02–T04 приняты как технологический выбор. Точные версии, параметры повторов/retention/онлайн-обновления и ожидаемый масштаб ещё не заданы; планы не обещают неустановленный SLO.
- Q06/Q07/Q15/Q16: нет новых endpoint ручного снятия, отзыва, отклонения апелляции до проверки, коррекции базы или публичной истории. Аномалии наблюдаемы; дальнейшее бизнес-действие требует отдельного решения.

Технические основания: [Microsoft — EF Core releases](https://learn.microsoft.com/en-us/ef/core/what-is-new/) указывает EF Core 10 для .NET 10; [RabbitMQ — acknowledgements/confirms](https://www.rabbitmq.com/docs/confirms) различает подтверждение публикации брокером и подтверждение обработки consumer. Конкретные API библиотек следует сверять при закреплении версий.
