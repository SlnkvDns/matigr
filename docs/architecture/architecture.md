# Архитектурная основа Matigr

Статус: **архитектурная основа**, актуализирована 23 октября 2026 года. Три связанные спецификации, затем их планы и задачи одобрены пользователем в этот день. Конкретные технические решения приняты в объёме планов; актуальный статус решений и оставшихся вопросов — в [согласовании контрактов](implementation-contracts.md). Одобрение не задаёт отсутствующие значения и будущие процессы. Код и исполняемая инфраструктура на текущем этапе не создаются.

Источник предметной области: [полная Event Storming диаграмма](../event-storming/tournament.mmd). Связанные документы: [карта контекстов](context-map.md), [контракты событий](event-contracts.md), спецификации [проверки](../specs/001-checking/spec.md), [результатов](../specs/002-results/spec.md), [апелляций](../specs/003-appeals/spec.md).

Факт согласования: 23 октября 2026 года пользователь сообщил «Я одобряю спецификации». Одобрение относится к текущим трём спецификациям с окончательным объёмом D24: Checking, Results и Appeals без загрузки/приёма/QR. Предварительное условие для планирования выполнено. Неизвестные ответы Qxx не подставляются; поручения на реализацию приложения этим сообщением не дано.

## 1. Как читать решения

- **Требование** — явно задано пользователем или содержится в диаграмме; при различии указана точка расхождения.
- **Предложение** — техническая или процессная рекомендация этого документа, требующая согласования.
- **Вопрос Qxx** — отсутствующее или неоднозначное бизнес-решение. Ни пример, ни предлагаемый статус не закрывают такой вопрос.

Диаграмма задаёт события и связи, но не является исчерпывающим регламентом. Названия английских контрактов, статусы, API, структура каталогов и механизмы надёжности ниже — предложения, а не уже существующие компоненты.

## 2. Цель и объём MVP

Проверяющий получает решение, фиксирует правильность либо передаёт его старшему жюри. Команда видит результат и таблицу. После публикации результата команда может подать допустимую по регламенту апелляцию; перепроверка подтверждает или изменяет результат. Изменение доходит до таблицы с отслеживаемым подтверждением.

Требуемый стек: C#, ASP.NET Core, .NET 10; React + TypeScript + Vite; собственная PostgreSQL БД каждого сервиса; API и асинхронные события; Docker Compose для локальной разработки.

По окончательному уточнению D24 объём — только Checking, Appeals и Results. Вне его весь приём/загрузка решений (включая фотографирование, QR и ручной выбор задачи), управление турниром/регистрациями команд, бланки и вопросы. Для тестов нужны уже принятые идентифицированные решения и готовые материалы, а не минимальный intake-продукт. По D23 допускается переключение тестовых пользователей с будущей заменой на полноценную регистрацию, без отдельного Identity-сервиса сейчас.

## 3. Предлагаемые сервисы и владение

| Сервис | Ответственность и данные | Не отвечает за |
| --- | --- | --- |
| Checking | Агрегат проверки/назначения/вердикты/история/перепроверки; локальный неизменяемый SolutionReference уже принятого решения и чтение материала; `checking_db` | Приём/загрузку/QR, агрегат подачи A6, баллы/публикацию, допустимость апелляции |
| Results | Результат команды по задаче, расчёт баллов, версия результата, публикация, история изменений, проекции команды и таблицы; `results_db` | Назначение жюри и рассмотрение апелляции |
| Appeals | Апелляция, проверка её допустимости по данным Results и регламенту, координация перепроверки, ожидание применения результата; `appeals_db` | Самостоятельный вердикт или запись баллов |

У каждого сервиса отдельный ASP.NET Core процесс, собственные миграции и учётные данные БД. Выделенные PostgreSQL контейнеры локально делают границу явной. В дальнейшем общий кластер допустим только с отдельными БД/ролями; общих таблиц и запросов между БД нет.

**Обоснование.** У проверки инвариант единственного активного исполнителя и собственная очередь; у результатов — единственный действующий результат и его версия; у апелляции — регламент и длительный процесс с ожиданиями. Их состояния и причины изменения различаются. Проверку и перепроверку выполняет один Checking: агрегат `A7` в диаграмме общий. Appeals не получает вторую реализацию оценки. Results — не только кэш: он владеет агрегатом `A8`, начислением баллов и опубликованной версией, а таблица — его производная модель.

По D24 ни Submission-сервис, ни модуль приёма внутри Checking не создаются. A6/приём материала принадлежат внешнему контексту вне текущего объёма. Checking получает уже идентифицированные solutionId/materialVersionId/tournamentId/teamId/taskId и стабильную ссылку на материал, сохраняет локальное представление и создаёт первичный Check идемпотентно. Для MVP предлагаются подготовленные fixtures через внутренний тестовый bootstrap; будущий входной контракт SolutionAccepted (E13) описывается отдельно от реализации его производителя. Не нужны API загрузки, синтетическое QR-распознавание или файловые операции приёма.

Авторизация — generic capability. D23 согласовал локальное переключение тестовых субъектов; предлагается изолированный доверенный issuer с фиксированными ролями/привязками. Его можно заменить полноценным входом/регистрацией без изменения доменных ID и правил доступа. Отдельный Identity-сервис сейчас не требуется.

Прочитаны все семь контекстов, четыре актора, три внешние системы и все переходы. Покрытие: `A1–A11`, `C1–C32`, `E1–E33`, `P1–P11`, `RM1–RM11`.

TEAM, JURY, SENIOR, ORG определяют разные возможности, но диаграмма не задаёт полную матрицу полномочий. FILE_STORAGE хранит материал решения; QR_DECODER исключён. NOTIFICATION — способ доставки обновлений, а не источник бизнес-состояния. E20/E23/E27 могут обновлять экраны; E29 исключено вместе с вопросами. WebSocket/Push в диаграмме не выбирает конкретную технологию и не гарантирует доставку.

### Неоднозначности диаграммы

1. `P5` объявлено, но не подключено стрелками. Текст прямо требует одного свободного задания одному проверяющему; это инвариант атомарного назначения.
2. `E19 → P6 → C19` требует передачи старшему, при этом SENIOR тоже связан с C19. Пользователь уточнил D03: старший выносит финальный вердикт, при недоступности работа ждёт в его очереди. Автоматический перевод в очередь в одной локальной транзакции остаётся техническим предложением.
3. `E13 → RM2` не показывает создание A7. Предлагается локально атомарно создавать первичную проверку после приёма материала; модель чтения не создаёт агрегат сама.
4. `C14 → A6 → E15` изображает закрытие приёма через одно решение. Это правило уровня турнира/окна, а не очевидный инвариант A6; в MVP только тестовая конфигурация, будущий владелец — Q14.
5. `P8/P9` идут после регистрации E23, отказ/просрочка не изображены. D10 задаёт срок подачи до конца турнира, D11 — ручной выбор членом жюри. В исходной диаграмме RM7 обновляется только по E24, но для ручного выбора нужен показ зарегистрированных E23 до принятия. Предлагается проверять допустимость при подаче и разделить регистрацию/ручное начало; сопоставление ручного начала C23/E24 и судьба недопустимых попыток ещё уточняются Q07.
6. `C24 → A7 → E25` пересекает контексты. Перепроверку создаёт Checking по запросу Appeals; Appeals не меняет A7 напрямую.
7. `E25 → C25/C26` не означает автоматический выбор вердикта при назначении: необходима работа проверяющего и завершение проверки.
8. `E26/E27 → C27`, а `E27 → C21` — параллельные ветви без подтверждения Results. Предлагается закрывать апелляцию после подтверждения обработки вердикта Results, в том числе при неизменном балле.
9. E21/E22 фиксируют результат, но отдельной публикации нет, хотя P8 её требует. Пользователь уточнил D06/Q01: Results публикует результат автоматически при обработке, включая коррекции по апелляциям.
10. Диаграмма не определяла повторные отправки и лимит назначений; пользователь уточнил их в D01/D02. D07 задал сумму и общее место при равенстве без тай-брейков, D08 — публичную таблицу с баллами по задачам. Повторные апелляции и возможное расширение бинарной оценки ещё обсуждаются.

## 5. Агрегаты и инварианты

| Агрегат/сущность | Граница и основные правила |
| --- | --- |
| SolutionReference, Checking | Не агрегат подачи A6, а локальный неизменяемый снимок уже принятого внешнего решения: solutionId/ключ турнира-команды-задачи/materialVersionId/materialRef/acceptedAt. D01 задаёт предпосылку одного решения по ключу; повтор входного факта не создаёт второй Check, несовместимый solutionId — ошибка входной целостности |
| Check / A7, Checking | Один активный исполнитель на Check и одна незавершённая работа на жюри. Отказ в первичной/апелляционной проверке передаёт тот же Check старшему (P6/D18); меняется назначение, не материал/appealId. Финальный бинарный вердикт без комментария D20. Предложение: новое рассмотрение по апелляции — отдельный Check, передача внутри него — история назначений |
| TeamTaskResult / A8, Results | Один действующий результат на `(tournamentId, teamId, taskId)`; P7: правильное → баллы задания, неправильное → 0. Не проверено ≠ 0. D06: автоматическая публикация. D07: сумма по задачам и общее место при равенстве. Предложение: версия результата и условное применение коррекции; источник баллов/его версия сохраняются |
| Appeal / A9, Appeals | Подача после публикации до ручного завершения организатором (D10/D16). Выбравший лично перепроверяет, включая первоначального жюри (D12/D15). Одна апелляция на команду/задачу/турнир; SeniorEscalation не обжалуется (D13/D14). Вовремя поданное можно брать и завершать после конца (D17). Предложение: адресованное назначение и закрытие после Results |

Очереди и таблица — модели чтения, а не отдельные агрегаты/микросервисы. При назначении Checking проверяет собственное актуальное состояние в БД, а не доверяет прочитанному списку. Inbox/outbox и журнал идемпотентности — инфраструктура, не бизнес-агрегаты. Не предлагается Event Sourcing: текущее состояние плюс история решений и интеграционных сообщений достаточно как исходная модель.

## 6. Процессы и транзакционные границы

### Первичная проверка

1. Checking получает уже принятое/идентифицированное решение через внутренний bootstrap подготовленных данных (в будущем — внешний SolutionAccepted). Локальные SolutionReference и первичный Check создаются атомарно/идемпотентно; этот шаг не принимает фото от команды, не декодирует QR и не владеет A6. Материал подготовлен заранее и читается через защищённый адаптер. Файлового приёма/очистки незавершённых загрузок в объёме нет.
2. Свободный член жюри атомарно берёт доступную проверку по любой задаче. Помимо исключения двух владельцев одного Check, нужна защита от двух разных назначений одному reviewerId (D02): проверка/ограничение занятости в той же транзакции, например уникальное активное назначение в БД. Для очереди возможен `FOR UPDATE SKIP LOCKED`, но он сам по себе не обеспечивает лимит жюри, а порядок/справедливость ещё не определены.
3. Жюри завершает проверку или отказывается. Завершение, освобождение занятости и outbox — одна транзакция Checking; после этого можно брать следующую работу, не ожидая Results. Отказ, освобождение обычного жюри и помещение в очередь старшего также атомарны, а не зависят от доставки брокером: после передачи обычный жюри сразу может брать следующую работу (D04). Старший берёт переданную, когда может проверять, и выносит финальный вердикт; очередь не является вторым активным назначением. Закрытие страницы/потеря связи сохраняет активное назначение и занятость, при возвращении оно читается из БД (D05).
4. Results получает вердикт, проверяет применимость, начисляет баллы и автоматически публикует результат в своей транзакции с inbox и outbox (D06). Принятие вердикта Checking ещё не означает завершённую обработку Results; после коммита Results отдельного шага публикации нет.
5. Таблица/результаты читаются из Results. Предложение: локальные проекции обновлять в той же транзакции либо строить запросом из его текущих данных, чтобы подтверждение Results не опережало доступный снимок результата. Push только сообщает об обновлении; клиент перечитывает API.

### Апелляция и перепроверка

1. Appeals синхронно получает из Results опубликованный снимок: ID/версию результата, вердикт/баллы, publicationId/publishedAt и decisionOrigin. SeniorEscalation обозначает финальный вердикт после обычного отказа, а не просто роль человека. Results не является владельцем конца турнира; при недоступности снимка допустимость не подтверждается по клиентскому экрану.
2. Appeals проверяет принадлежность, открытость подачи до ручного конца (D10/D16), запрет D14 и отсутствие прежней апелляции по ключу (D13). Регистрация, уникальный ключ и время/основание допуска сохраняются локально атомарно. Registered виден жюри до начала (D11); одной подачей Check не создаётся. Предложенный порт ручного конца и точка согласованности описаны ниже; запрос на границе ещё требует согласования Q02.
3. Свободный жюри, в том числе первоначальный проверяющий, вручную выбирает и лично перепроверяет (D11/D12/D15), даже после конца турнира для ранее поданной апелляции (D17). Предложение: выбор/попытка/outbox сохраняются в Appeals; Checking атомарно создаёт Check и назначает requestedReviewerId при общей свободной занятости, затем подтверждает. До ответа UI показывает ожидание. При ReviewerBusy Check не создан, та же апелляция возвращается к выбору; после подтверждённого отказа новая попытка возможна с прежним Appeal/квотой. Состояние Closed турнира не является основанием отказать этому назначению. Технический протокол остаётся предложением.
4. Проверяющий завершает её. Checking публикует `CheckCompleted` с `appealId`, базовой версией результата и идентификатором исходного вердикта. Appeals переходит к ожиданию Results; событие может прийти позже подтверждения Results, поэтому обработчики не требуют такого порядка.
5. Results применяет вердикт только к ожидаемой версии результата. Новый вердикт заменяет значение баллов, а не добавляет их ещё раз. Подтверждение неизменного результата тоже требует проверки версии и зарегистрированной обработки.
6. Results автоматически публикует коррекцию и затем отправляет из outbox `ResultEvaluationApplied` с идентификатором обработанной проверки, итоговой версией, публикацией и признаком изменения. При подтверждении без изменения указывается прежняя доступная публикация. Appeals закрывает процесс только при совпадении апелляции, проверки и ожидаемой базы; дополнительного состояния ожидания публикации нет (D06). При конфликте — `ResultEvaluationRejected`, состояние требует разрешения; автоматической перезаписи/нового вердикта нет.

При отказе уже назначенного апелляционного жюри действует D18: Checking в одной транзакции снимает его назначение/занятость, переводит тот же Check в SeniorQueued и сохраняет outbox RecheckEscalated. Свободный старший берёт его из своей очереди и завершает, в том числе после конца. Предлагается повторно использовать RecheckAssigned для нового персонального назначения с признаком SeniorEscalation. Последующие CheckCompleted/подтверждение Results содержат фактического старшего и цепочку передачи, а не притворяются оценкой первоначально выбравшего. Задержанные промежуточные события не должны блокировать корректное итоговое подтверждение или откатывать состояние.

Распределённая транзакция не предлагается. Это процесс с устойчивым состоянием, повторами и явными промежуточными этапами. Компенсация не должна стирать вынесенный вердикт; неуспешный процесс сохраняется для восстановления. Само закрытие апелляции не запускает вторую коррекцию результата.

## 7. API и асинхронность

Синхронные API: браузер → профильный сервис (команды, чтение, материал); Appeals → Results (проверяемый опубликованный снимок). API не удерживает транзакцию во время ожидания другого сервиса. Межсервисный доступ аутентифицируется отдельно от пользовательского, идентификаторы субъектов берутся из проверенного удостоверения.

Асинхронность: Checking → Results (вердикты), Appeals → Checking (запрос перепроверки), Checking → Appeals (принятие запроса/завершение), Results → Appeals (применение/конфликт). Детали — [event-contracts.md](event-contracts.md). Брокер отвечает за транспорт, бизнес-очереди остаются в Checking/Appeals. Предложение кандидата — RabbitMQ с устойчивыми очередями; продукт, библиотека клиента и версии пока не выбраны (Q13).

Для онлайн-таблицы предлагается публичный API снимка плюс канал обновлений Results; выбор SSE, ASP.NET Core SignalR/WebSocket либо polling зависит от Q10 и оставшихся деталей Q16. По D08 вход не требуется для таблицы и её публичных обновлений. Даже с push нужен повторный запрос после разрыва; публичный канал не содержит материалов/служебных данных. Клиент не соединяется с брокером. Gateway не обязателен: локальный Vite proxy, позже простой reverse proxy; отдельный BFF вводить только при доказанной необходимости.

### Ручное завершение и граница подачи в MVP — техническое предложение

Бизнес-факт D16 соответствует C9/E9 полного турнирного контекста, который остаётся вне MVP. Для сквозного теста предлагается изолированный development/test-адаптер ввода факта ручного завершения от организатора. Он не создаёт/редактирует турнир, команды или задачи и не является полноценным Tournament-сервисом. Успех тестового действия подтверждает закрытие подачи апелляций в тестовом сценарии; фиксируются factId, tournamentId, субъект и серверное время. Заранее заданное endsAt и таймер не заменяют действие организатора.

Appeals хранит локальную служебную запись окна подачи по tournamentId: Open/Closed, версию и основание завершения. Это его граница допуска, а не копия всего агрегата Турнир. Предложение для гонки: перед финальной регистрацией брать блокировку этой записи и в одной транзакции проверять Open/уникальный ключ и сохранять Appeal. Закрытие использует ту же запись/блокировку. Вызов Results выполняется до этой транзакции, чтобы не удерживать блокировку во время HTTP. При таком варианте порядок допуска и закрытия определяет БД; согласование этого конкретного критерия для запроса, начатого до конца, но дошедшего позже, остаётся частью Q02. ReceivedAt сохраняется для аудита, но само по себе не обходит Closed. Идемпотентный повтор ранее успешной подачи возвращает исходный Appeal и после закрытия.

После конца новые апелляции закрыты, но Registered, назначения/передачи/повторы и публикация продолжаются (D17/D18). Ранее принятые первичные решения также проверяются (D19), даже если внешнее подтверждение принятия/тестовый bootstrap доставлены позже. P4 относится к внешнему контексту приёма: Checking не реализует его закрытие и не отвергает уже принятый материал по текущей неактивности. Конец не означает неизменность таблицы.

В будущем подлинным источником E9 будет турнирный контекст. Простое асинхронное обновление локального флага оставляет окно между фактическим концом и доставкой сообщения; его нельзя выдавать за строгий запрет поздней подачи. Потребуется согласовать единый авторитет допуска/протокол закрытия с upstream. Синхронное чтение статуса без атомарного допуска также не устраняет гонку. Отдельный контракт источника окончания сейчас не фиксируется как реализованный сервис.

## 8. Согласованность и конкуренция

| Риск | Предлагаемая защита и предел гарантии |
| --- | --- |
| Два жюри берут одну запись | Атомарное назначение в Checking, версия Check и assignment token; список очереди только подсказка |
| Один жюри берёт две разные работы одновременно | Согласованный D02 требует уникального активного назначения по reviewerId и атомарного захвата вместе с проверкой занятости. Проверки только одной строки Check недостаточно; лимит общий для очередей, а не на вкладку |
| Вердикт одновременно с отказом/переназначением | Условный переход по версии и актуальному назначению. Побеждает одна транзакция; проигравший получает конфликт, а не молчаливый успех |
| Проверяющий закрыл страницу/потерял связь | По D05 назначение и занятость сохраняются, при возвращении читаются из БД; автоматическое освобождение/lease по отсутствию клиента не используется. Ручное освобождение длительно зависшей работы и полномочия остаются открытыми (остаток Q06); если его согласуют, старый token после освобождения недействителен |
| Коммит прошёл, публикация сообщения упала | Outbox в транзакции с бизнес-записью; повторная доставка. Inbox и бизнес-обработка — одна транзакция потребителя |
| Повтор команды/события | Idempotency key с hash запроса и сохранённым ответом; inbox по messageId, бизнес-уникальность по checkId/appealId. Одинаковый key с другим телом — конфликт |
| События пришли в другом порядке | Не использовать время как порядок. aggregateVersion относится только к своему потоку; reviewRevision — к решению; expectedResultVersion — к результату. Пробелы/отсутствующие зависимости удерживать до разбора, а не принимать «последнее пришедшее» |
| Повторная/конкурентная подача апелляции | D13: постоянный уникальный ключ tournamentId/teamId/taskId в Appeals, не частичный индекс активных и не ключ версии результата. Идентичный технический повтор возвращает тот же Appeal; новая бизнес-подача после Closed тоже запрещена. Checking дедуплицирует по appealId, Results использует CAS |
| Два жюри выбирают одну апелляцию / выбранный жюри одновременно берёт обычную работу | По D12 выбор адресуется тому же reviewerId. Предложение: один переход Registered по версии; конкретное назначение атомарно подтверждает Checking. При ReviewerBusy нет назначения, та же апелляция снова доступна после подтверждённого отказа. Запоздалые ответы сопоставляются ID попытки; отдельного лимита занятости Appeals нет |
| Старший завершил апелляцию, но Appeals ещё не получил событие передачи | Итог несёт actual reviewerId, selectedReviewerId, assignmentId и escalationId/происхождение. Проверять разрешённую цепочку D18, не требовать равенства фактического жюри исходному выбравшему. Состояния назначений сравнивать по версии Check; позднее RecheckEscalated не откатывает Closed |
| Между чтением публикации и вердиктом результат изменился | Снимок публикации и проверка версии в Results при применении. Первое чтение не резервирует результат и не устраняет гонку. Устаревшая перепроверка требует решения Q15 |
| Несовместимый внешний solutionId для уже занятого ключа | D01 задаёт предпосылку одного принятого решения; D24 исключил сам приём. Checking обнаруживает конфликт локального SolutionReference, Results не выбирает «лучшую/последнюю» отправку. Повтор снимка идемпотентен, для перепроверок сохраняется CAS базы |
| Стоимость задачи/версия фикстур не совпали между запуском и восстановлением | По D22 стоимость во время турнира неизменна; сохранять исходный набор/версию, обнаруживать несовпадение, не пересчитывать историю из другого набора. API изменения стоимости в MVP не предлагается |
| Две задачи одной команды оценены одновременно | Сумма не обновляется как небезопасное read-modify-write. Предложение: вычислять из согласованного снимка результатов либо обновлять агрегированную сумму транзакционно без потери вклада; общий рейтинг пересчитывается по доступному снимку, равные суммы сохраняют общее место (D07) |
| Закрытие раньше отражения в таблице | Сначала Results фиксирует авторитетный результат и доступный снимок, затем outbox-подтверждение; только после него Appeals закрывается |
| Брокер/потребитель недоступен | Локальные операции сохраняют outbox; UI показывает ожидание. Отслеживать возраст outbox, очередь ошибок и незавершённые апелляции; граница допустимой задержки — Q10 |
| Организатор завершает турнир одновременно с подачей / конец задержался в брокере | По D16 конец ручной; предлагается сериализовать регистрацию и закрытие на записи окна Appeals в тестовом адаптере. Асинхронный флаг не обеспечивает точную границу. Конкретная точка допуска пограничного запроса ещё Q02. По D17 поданные вовремя остаются доступными после конца; дубль возвращает прежний Appeal, не становится новой подачей |
| Сброс одной БД и replay | Inbox не заменяет источник восстановления. Нужны история проверок/результатов, снимки и согласованное восстановление; нельзя обещать полный replay из брокера без retention-контракта (Q13) |

Уровень согласованности: строгий внутри локального агрегата/транзакции; eventual consistency между сервисами. Нельзя гарантировать мгновенный общий снимок трёх БД. Таблица показывает версию снимка и время формирования, но это не доказательство отсутствия сообщений в пути.

## 9. Минимальная тестовая среда и права

Предложение: версионируемые fixtures турнира/команд/задач/неизменных стоимостей (D22), субъектов и уже принятых решений с готовыми материалами. Каждый сервис инициализирует только свои данные с согласованными ID/версией, без общей runtime-БД. Checking проверяет целостность ссылок входного снимка и не создаёт дубли Check, но не выполняет бизнес-приём, QR или P4 внешнего контекста. Несовпадение обязательных версий набора — наблюдаемая ошибка, не начисление 0.

Роли: команда — материал/результаты/одна апелляция своей команды, кроме D14; жюри — собственные назначения и лично выбранная апелляция, в том числе своя прежняя работа (D12/D15); старшее жюри — отдельная очередь; организатор — чтение и ручное завершение как бизнес-факт D16, вводимый в MVP через тестовый адаптер. Таблица публична, материал/команды изменения — отдельно защищены. Отклонение/отзыв ещё Q07; дополнительные публичные поля — Q16.

D21 описывает будущую фотографию листа с QR; D24 явно исключил весь этот приём из текущего объёма. Для сквозного теста материал уже существует, доступен жюри на чтение и связан с подготовленным SolutionReference. Предложение: приватный read-only fixture-volume/адаптер материала, без upload endpoint и записи фото пользователем. Production-владелец исходного материала — внешний контекст, его storage API не реализуется сейчас. В контракте только стабильный materialRef, не бинарный файл/истекающая URL.

По D23 локальный MVP использует переключение заранее заданных тестовых субъектов команд/жюри/старшего/организатора. Dev-вход включён только в явном development-профиле; доверенное удостоверение и роли/scope проверяются backend. Произвольный role/team header браузера не является удостоверением. JWT/cookie и библиотека — технические детали, ещё не выбранные. При смене субъекта frontend очищает приватный кэш; сохранённое назначение принадлежит субъекту в БД, а не вкладке.

Будущая полноценная регистрация — требование заменяемости D23, не поручение реализовать её сейчас. Предложение: поставщик входа за адаптером выдаёт нормализованный контекст стабильного внутреннего subjectId, команды/ролей/scope; бизнес-сервисы сохраняют собственную проверку полномочий. При подключении настоящего IdP внешний `(issuer, subject)` связывается с прежним внутренним ID, чтобы не переписывать reviewerId в истории и не терять назначения. Пароли/email/названия тестовых пользователей не становятся ключами агрегатов. Frontend использует общий интерфейс сессии; dev-переключатель заменяется входом/регистрацией. Владение аккаунтами/подтверждение регистрации согласуются на будущем этапе, без новых auth-таблиц и сервиса сейчас.

## 10. Предлагаемая организация monorepo

Ниже целевая схема, не поручение создать каталоги или проекты сейчас.

```text
AGENTS.md
docs/
  event-storming/tournament.mmd
  architecture/{architecture,context-map,event-contracts}.md
  specs/{001-checking,002-results,003-appeals}/spec.md
src/
  backend/
    Matigr.slnx
    services/
      Checking/{Checking.Api,Checking.Application,Checking.Domain,Checking.Infrastructure}/
      Results/{Results.Api,Results.Application,Results.Domain,Results.Infrastructure}/
      Appeals/{Appeals.Api,Appeals.Application,Appeals.Domain,Appeals.Infrastructure}/
    building-blocks/                 # только технические средства при реальной потребности
  frontend/
    apps/web/                       # один React + TypeScript + Vite клиент
      src/
        app/                        # маршрутизация, композиция, dev-профиль
        features/{checking,results,appeals}/
        shared/{api,ui,auth}/
contracts/
  http/{checking,results,appeals}/    # OpenAPI после согласования API
  events/                           # схемы опубликованных контрактов
tests/
  backend/{Checking,Results,Appeals}/
  contracts/
  integration/
  e2e/
infra/
  compose/                          # будущий Compose и локальная конфигурация
  fixtures/                         # согласованные тестовые данные
```

Разделение API/Application/Domain/Infrastructure предлагается для изоляции бизнес-правил от ASP.NET, БД и брокера; если размер сервиса этого не требует, допустимы папки в одном проекте. Domain не ссылается на ASP.NET, чужие сервисы или брокер. У каждого сервиса свои миграции и тесты. Сервисы не ссылаются на Application/Domain/Infrastructure соседей. Общий solution облегчает сборку, но не создаёт общий deployable.

`building-blocks` не содержит Team, Check, Result или Appeal. Не создавать его заранее ради абстракций. Общие схемы сообщений не являются shared domain library; версии производителя и потребителя должны иметь возможность разойтись совместимым образом. Frontend получает DTO из OpenAPI; общие UI-компоненты не хранят правила начисления. Серверные данные кэшируются по турниру/команде/версии и сбрасываются при смене тестового пользователя. Менеджер пакетов и библиотеки состояния/запросов не выбираются без необходимости.

## 11. Будущий Docker Compose

Предлагаемый состав: checking-api/results-api/appeals-api, три PostgreSQL с раздельными volumes/ролями, брокер и web/Vite в dev-профиле. Готовые материалы монтируются read-only для тестового адаптера чтения, без upload/QR/storage-сервиса приёма. Образы/пакеты фиксируются после согласования, без latest.

Нужны проверки готовности БД/брокера/API, контролируемое применение миграций и импорт версии фикстур, восстановление соединений и устойчивые outbox workers. Порядок старта контейнеров не заменяет повторы подключения. Каждая БД доступна только своему сервису; браузер видит API через локальный proxy. Секреты локальной среды не хранятся в Git. Точный файл Compose сейчас не создаётся.

Предложенные наблюдаемые признаки: correlationId, causationId, checkId/resultId/appealId, assignmentId/escalationId; возраст outbox/inbox ошибок, конфликты, зависшие процессы; структурированный аудит субъекта/переходов. Комментарий/текст причины вердикта от жюри не требуется (D20). Технические reasonCode ошибок не являются таким комментарием. SLO/retention не выдумываются.

## 14. Технические основания

- Целевая платформа задана пользователем; .NET 10 и соответствующий ASP.NET Core входят в поддерживаемую линейку: [официальный lifecycle .NET](https://learn.microsoft.com/en-us/lifecycle/products/microsoft-net-and-net-core). Точный SDK/patch будет фиксироваться при реализации.
- Outbox и идемпотентная обработка предлагаются для разрыва между транзакцией БД и доставкой: [Microsoft: подписка и надёжность интеграционных событий](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/multi-container-microservice-net-applications/subscribe-events), [интеграция через события](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/multi-container-microservice-net-applications/integration-event-based-microservice-communications).
- `SKIP LOCKED` допустим для очередей, но не даёт согласованный произвольный снимок или бизнес-порядок: [PostgreSQL: SELECT / Locking Clause](https://www.postgresql.org/docs/18/sql-select.html). Ссылка на документацию 18 не фиксирует версию PostgreSQL проекта.
