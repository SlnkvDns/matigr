## Linux-права ключей

В [следующем запуске на 7a8a17e](https://github.com/SlnkvDns/matigr/actions/runs/40306728216) checking job успешен, infrastructure дошёл до check-results-http: личные результаты вернули 500. Причина воспроизведена на отдельном `matigr-ci-http-20261026`: `UnauthorizedAccessException` при чтении `/run/secrets/dev_issuer_public` от UID 1654 при владельце root и mode 600. На Windows обычный bind mount скрывал проблему Linux-прав.

Results теперь копирует пользовательский и сервисный public key в `/run/matigr-identity`, Appeals — пользовательский public key в `/run/matigr-service`; файлы принадлежат UID 1654, mode 600, каталоги mode 700. Compose указывает runtime-пути. Ключи на хосте не изменяются, доступ к private key пользовательского issuer остаётся только у Checking. check-infrastructure проверяет чтение от UID 1654 и владельца/mode каждого используемого runtime-ключа. Workflow при падении выводит состояние контейнеров и ограниченный журнал API до остановки стека.

Пересобраны Results/Appeals. Для Linux-регрессии временный override монтирует исходные secrets отдельно, затем делает только внутри контейнера root:600 копии в tmpfs `/run/secrets`. С прежним entrypoint воспроизведён исходный 500, с исправлением полностью прошли check-infrastructure, check-results-http, authenticated GET собственных апелляций, identity restart, Checking work/restart и transitions. Данные исходного пользовательского стека не используются. Глобальные SDK/права host-файлов/ключи не менялись.
