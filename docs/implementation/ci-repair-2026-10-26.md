## Linux-права ключей

В [следующем запуске на 7a8a17e](https://github.com/SlnkvDns/matigr/actions/runs/40306728216) checking job успешен, infrastructure дошёл до check-results-http: личные результаты вернули 500. Причина воспроизведена на отдельном `matigr-ci-http-20261026`: `UnauthorizedAccessException` при чтении `/run/secrets/dev_issuer_public` от UID 1654 при владельце root и mode 600. На Windows обычный bind mount скрывал проблему Linux-прав.

Results теперь копирует пользовательский и сервисный public key в `/run/matigr-identity`, Appeals — пользовательский public key в `/run/matigr-service`; файлы принадлежат UID 1654, mode 600, каталоги mode 700. Compose указывает runtime-пути. Ключи на хосте не изменяются, доступ к private key пользовательского issuer остаётся только у Checking. check-infrastructure проверяет чтение от UID 1654 и владельца/mode каждого используемого runtime-ключа. Workflow при падении выводит состояние контейнеров и ограниченный журнал API до остановки стека.

Пересобраны Results/Appeals. Для Linux-регрессии временный override монтирует исходные secrets отдельно, затем делает только внутри контейнера root:600 копии в tmpfs `/run/secrets`. С прежним entrypoint воспроизведён исходный 500, с исправлением полностью прошли check-infrastructure, check-results-http, authenticated GET собственных апелляций, identity restart, Checking work/restart и transitions. Данные исходного пользовательского стека не используются. Глобальные SDK/права host-файлов/ключи не менялись.

## Гонка HTTP-readiness после crash/recovery

В [запуске на 019950a](https://github.com/SlnkvDns/matigr/actions/runs/40309430005) checking job и предыдущие runtime-шаги infrastructure прошли, включая ключи, HTTP, transport и SSE. check-checking-faults упал после восстановления outbox: запрос `/health/ready` попал в ещё запускающийся HTTP listener и получил `fetch failed`, причина `UND_ERR_SOCKET: other side closed`. Обёртка eventually повторяла неподходящий HTTP-статус, но не сетевое исключение. Локальный прежний успешный прогон не воспроизводил это временное окно.

Тест теперь использует `scripts/http-test-support.mjs`: повторяет только ожидаемые сетевые ошибки startup/readiness и timeout запроса, ждёт HTTP 200, сохраняет общий deadline 60 секунд, ограничивает отдельный запрос двумя секундами. Неверный URL/прочие программные ошибки не подавляются. Бизнес-команды и SQL не получают автоматических повторов.

Добавлены четыре `tests/integration/http-readiness.test.mjs` без Docker/внешних зависимостей: реальный закрытый сокет → HTTP 503 → HTTP 200, постоянный 503 до deadline, зависший запрос до deadline, немедленная ошибка неверного URL. До исправления первый тест воспроизвёл `fetch failed`; с исправлением все четыре прошли. Набор включён в infrastructure CI до Compose и в `scripts/check.ps1`.

На свежем `matigr-ci-readiness-20261026` отдельно прошли оба последних шага workflow: CHK-IT-04 (SIGKILL после confirm до Sent, recovery, единственная публикация, HTTP replay) и RES-IT-02 (defer/quarantine, restart, audited redrive, дубли, poison). Более ранние шаги уже прошли в указанном удалённом запуске; весь набор заново не повторялся. YAML workflow, синтаксис изменённых scripts, документация, архитектура и Git diff проверены. Production-код, контракты бизнес-процессов и данные не менялись.

Docker снова потерял движок до запуска тестового стека; выполнен разрешённый перезапуск с сохранением временного run как `run-matigr-backup-20261026-readiness-165000`. Тестовый стек остановлен, volumes/ключи сохранены. На момент записи новое исправление локальное, новый удалённый CI с ним не запускался.
