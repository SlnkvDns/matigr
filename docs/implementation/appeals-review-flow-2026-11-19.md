# Первая апелляция после вердикта старшего и рабочее место жюри

19 ноября 2026 года пользователь попросил разрешить первую апелляцию после первичного вердикта старшего жюри и сделать интерфейс апелляций понятнее. Это меняет исходный D14. Дата согласования первоначального MVP сохраняется.

## Поведение и критерии приёмки

- После публикации первичного вердикта команда может подать апелляцию до ручного окончания турнира. Вердикт обычного или старшего жюри обрабатывается одинаково. Checking подтверждает перепроверку на том же материале, Results применяет её итог, Appeals закрывает обращение после подтверждения публикации.
- Appeals разрешает одну подачу по ключу турнир, команда, задача. Одновременные подачи с разными ключами дают один успех. После закрытия и изменения балла новая подача по той же задаче отклоняется. Повтор успешного запроса с тем же ключом возвращает исходную регистрацию.
- Жюри видит очередь с названиями команд и задач и действием «Взять на перепроверку». После выбора интерфейс показывает ожидание, а при подтверждении личного назначения предлагает открыть проверку. Если назначение сорвалось из-за уже открытой работы, жюри получает понятный следующий шаг. Команда видит, по какой задаче подано обращение и на каком этапе оно находится.

## План работ

1. Убрать ограничение по происхождению первичного вердикта в допуске и назначении, сохранив проверку основания и постоянную квоту. Обновить HTTP-описание и известных потребителей. Учитывать ранее записанные события при чтении.
2. Обновить экран апелляций для жюри и команд. Названия брать из опубликованного состава турнира в Results, решения о доступе и состоянии — из API.
3. Проверить допуск, конкурирующие подачи, повтор команды и полный сценарий от вердикта старшего до закрытия апелляции. Проверить UI на локальном изолированном стенде.

## Реализация и проверка 19 ноября

- Новая регистрация опирается на D13, серверное окно и актуальное опубликованное основание. Checking принимает завершённый первичный Check с `OrdinaryReview` или `SeniorEscalation`. Исторический `BaseNotAppealable` остаётся допустимым в событиях v1 для ранее сохранённых сообщений. Миграции БД не понадобились.
- Через веб-прокси стенда `matigr-appeals-flow` проверен путь P6/E20 → E21 → C22 → C23/C24 → E27 → E28. Старший выносит первичный Incorrect, из двух параллельных подач проходит одна, повтор прежнего ключа возвращает её же. Checking назначает перепроверку того же материала. После Correct балл меняется с нуля на стоимость задачи, апелляция закрывается, новый запрос по текущей версии получает `409 AlreadyAppealed`.
- В браузере под «Жюри 1» открыта очередь с названиями команд и задач. Проверены действие «Взять на перепроверку», подтверждение назначения и ссылка «Открыть перепроверку». В открытой демоверсии одна апелляция назначена и ещё одна доступна в очереди. Стенд использует отдельные базы на портах API 5301–5303 и веб-интерфейс на 5175.
- Проверены 227 backend-тестов, из них 35 тестов предметной логики Checking прошли отдельным повтором после исправления тестовых данных. Frontend: 110 тестов, typecheck и production-сборка. Контракты: 99 тестов, совпадение сгенерированных типов с OpenAPI. Checking/PostgreSQL: 47 тестов и отдельная проверка восстановления назначения после перезапуска. Appeals/PostgreSQL и RabbitMQ: 31 тест на повторно запущенном изолированном окружении после временного сбоя запуска тестового брокера.
